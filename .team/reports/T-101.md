### Existing contracts to reuse

Fresh partial-subset cleanup should remain a worker-loss operation. It should
not use `AppRevisionCleanup` directly: that class deliberately requires a new
revision with completed HTTP readiness evidence before it removes older IDs
(`labs/eru-vps-mvp/scripts/app_cleanup.py:31-77,93-147`), whereas worker-loss
cleanup must remove fenced stale metadata before a replacement is created.

Reuse or extend these worker-loss primitives:

  (`scripts/worker_loss_executor.py:22-24`).
- `plan_digest()` and `_seal()` for canonical hash binding

  not an authorization signature; source-plan provenance still has to be
  checked.
- `_control_binding()`, `_workload_binding()`, `_node_static_digest()`,
  `_target_fenced()`, and `_usage_state()` for the fresh baseline and fence /

  unavailable+bypassed target checks (`scripts/worker_loss_executor.py:93-102`;
  `scripts/worker_loss_adapter.py:34-120`). The adapter intentionally never SSHs

- `_review_targets()` and `_target_matches()` for exact ID, node, owner,

- The exact read states `absent`, `present_exact`, `identity_changed`, and
  `query_failed`, plus two stable snapshots, from `_reconcile_locked()`

- `_load_plan()`, `_write_plan()`, `ClusterLock`, private-path/symlink checks,

### Required invariants

1. The lost worker remains externally fenced, `available=false`, and
   `bypass=true`; provider/network fence evidence remains caller attestation,
   not provider-API verification (`docs/M3-WORKER-LOSS-PREP-2026-09-27.md:7-17,47-60`).
2. No operation contacts the lost target. Reads use core plus healthy workers;
   the only cleanup mutation is one core-side `workload dissociate EXACT_ID`.
3. Every mutation plan has a fresh ID and its own journal. A source plan that
   has any journal is never replayed (`scripts/worker_loss_executor.py:341-343`),
   including when its latest reconciliation reports a safe remaining subset.
4. The partial subset is derived only from fresh exact-ID reads: include every
   and only original target in state `present_exact`; exclude only IDs proven
   `absent`; block on `identity_changed`, `query_failed`, duplicates, omissions,
   or an empty subset.
5. Each remaining ID retains the complete original target identity
   (`id`, `node`, `logical_app`, `spec_sha256`, `appname`). Never accept an
   ID-only caller-supplied subset; `remaining_exact_ids` must be joined back to
   validated source `targets`.
6. Before sealing a fresh cleanup plan, require two stable, clean snapshots,
   the same reviewed worker membership/static node digest and target fence, the
   exact full workload identity set implied by reconciliation, and a freshly
   bound quota digest. The executor's first preflight must match that new
   baseline exactly (`scripts/worker_loss_executor.py:358-364`).
7. Journal intent is durable before each dissociation. A lost reply is followed
   by one exact read; if the ID is not proven absent, stop uncertain and never
   retry from that plan (`scripts/worker_loss_executor.py:375-423`).
8. After each mutation, the only permitted full-cluster identity delta is the
   reviewed exact ID. Extra/missing/changed workloads, worker inconsistency,
   target fence drift, or node identity drift stops the run.
9. Replacement planning is allowed only after all original stale IDs are
   absent, two snapshots are stable/clean, and target quota is exactly zero.
   Nonzero quota remains operator review; never call `resource --fix`
   (`scripts/worker_loss_executor.py:429-449,528-542`).
10. `replacement_plan_allowed` proves only stale-state clearance. It does not
    prove provider fencing independently, desired-spec availability,
    destination capacity, ERU create success, or HTTP readiness.
11. Desired specs must be supplied again from protected input and must match
    every original move's logical app, source spec hash/appname/replicas, and
    destination spec hash/appname. The destination worker must still be a
    reviewed healthy worker and must remain available/not bypassed.
12. Replacement plans must be made one app at a time against a fresh live
    snapshot. Creating several executable ERU-012 plans from one snapshot is
    unsafe because the first deploy invalidates every later plan's
    `snapshot_sha256`; `AppExecutor` correctly rejects that drift
    (`scripts/app_executor.py:221-247`).
13. ERU core's create is the authoritative capacity admission. Do not promote
    the planner's destination selection to a capacity guarantee
    (`scripts/app_executor.py:50-57`).
14. Hold one shared `ClusterLock` around each mutation. If a coordinator holds
    it, call the child's `_execute_locked()` as ERU-009 does
    (`scripts/worker_drain_executor.py:420-426,483-496`); do not nest public
    `execute()` calls that acquire the same nonblocking lock.
15. Exact workload IDs remain private. Public command output should expose
    counts, gates, plan IDs/hashes, and private paths only
    (`docs/M3-WORKER-LOSS-PREP-2026-09-27.md:34-45`).

### Coupling and ambiguity that must be resolved fail-closed

- A worker-loss journal is not self-sufficient source-plan evidence. It stores
  `plan_sha256` but not the complete execution plan, and current recovery checks
  only a small journal shape (`scripts/worker_loss_executor.py:463-483`). A
  builder must load the immutable saved execution plan through `_load_plan()`,
  verify its digest, then require exact journal/plan equality for source ID,
  plan hash, review hash, target, destinations, targets, and baseline. Trusting
  the mutable journal or its gate booleans alone would allow a rehashed or
  edited source record to authorize mutation.
- `fresh_cleanup_plan_allowed` is a recovery conclusion, not a durable live
  lease. Recovery persists no full second snapshot inside the reconciliation
  object. Planning must query again and hash-bind fresh state; it must not copy
  the boolean into an executable plan.
- `_validate_plan()` currently validates shape and self-digest but does not
  prove that a semantically valid rehashed target subset was authorized by a
  source plan (`scripts/worker_loss_executor.py:300-333`). A recovery-derived
  plan therefore needs explicit source bindings that are revalidated before
  execution, not merely extra informational fields.
- The review plan and journal contain hashes/identities, not the full original
  desired app documents. Replacement planning must require the original
  private input again, rebuild/verify the saved review plan as
  `prepare_execution_plan()` already does (`scripts/worker_loss_ops.py:98-113`),
  and validate destination specs using the ERU-009 pattern.
- `WorkerLossCLIAdapter.preflight(snapshot, target, destinations)` is not the
  one-argument `AppExecutor` adapter contract (`scripts/worker_loss_adapter.py:44-50`;
  `scripts/app_executor.py:95-104`). Planning can call worker-loss preflight and
  the pure `app_executor.execution_plan()`, but actual replacement execution
  needs the established ERU-012 deploy/list/probe adapter or a narrow composite
  adapter. Do not weaken either interface by skipping checks.
- `AppRevisionCleanup` is intentionally ordered after replacement readiness;
  it cannot be used as the pre-replacement worker-loss cleanup executor. Only
  its source-binding/subset concept (`scripts/app_cleanup.py:149-174`) is
  reusable.

### Narrowest safe implementation boundary

1. Add one recovery cleanup plan builder plus private ops persistence. Inputs:
   immutable source execution plan, its source journal/run ID, a caller-chosen
   fresh plan ID, and the worker-loss API. Under `ClusterLock`, validate the
   source plan and all plan/journal bindings, perform fresh exact reconciliation
   plus two stable snapshots, and derive the full remaining target rows.
2. Seal an ordinary executable `worker-loss-stale-cleanup-plan` with the fresh
   ID, only the remaining target rows, and a new baseline. Add a mandatory
   `recovery_source` block containing at least `run_id`, `plan_sha256`,
   `review_plan_sha256`, sorted confirmed-absent original IDs, and the fresh
   reconciliation/baseline digest. Extend `_validate_plan()` to validate this
   provenance against the immutable source plan and journal before mutation.
   Store it in a separate private category so the source plan/journal remain
   immutable history.
3. Reuse `WorkerLossExecutor` unchanged for sequencing where possible; only
   extend validation/provenance. A fresh journal follows automatically because
   the new plan ID differs. Do not add a resume/replay path.
4. Add a separate replacement-plan operation that performs no deploy. It loads
   and validates the completed worker-loss journal and immutable source plan,
   reruns stable recovery, requires `replacement_plan_allowed`, rereads and
   rebuilds the original private review input, validates all desired specs, and
   selects exactly one not-yet-satisfied logical app in deterministic reviewed
   order.
5. For that one app, change only `node` to the reviewed destination, recompute
   and compare `spec_identity()` with the review move's replacement identity,
   take a fresh snapshot/preflight, and call
   `app_executor.execution_plan()` with a fresh ERU-012 plan ID. Persist the
   resulting ERU-012 plan using existing private-plan safeguards. Execute it
   through the existing `AppExecutor`; create the next app plan only after the
   prior child journal and a new snapshot prove the resulting revision.
6. Stop this slice at plan creation (and existing ERU-012 execution wiring if
   already exposed). Do not add node removal, quota repair, target recovery,
   provider APIs, automatic selection of a different destination, or a
   same-snapshot multi-app plan bundle.

This boundary preserves the architecture statement that recovery may open a
gate but every subsequent mutation comes from a new hash-bound plan
(`docs/M3-WORKER-LOSS-PREP-2026-09-27.md:51-60`).

## Risks and Follow-ups

- Highest risk: deriving a mutation plan from the mutable recovery journal or
  `fresh_cleanup_plan_allowed` boolean without reloading the hash-bound source
  execution plan and rebinding fresh live state.
- High risk: issuing multiple replacement plans from one snapshot; later plans
  are necessarily stale after the first deploy.
- High risk: treating an original review destination as proof of current
  capacity. Admission remains authoritative only at ERU create time.
- Medium risk: adapter mismatch between worker-loss preflight and the full
  ERU-012 deploy/list/probe contract. Resolve with explicit composition, not
  duck-typed omission of checks.
- Medium risk: older journals do not embed the full source plan. Keep backward
  compatibility by loading the saved execution plan rather than changing past
  journal meaning.
- Follow-up: independently review the final provenance validation and tests for
  semantically valid rehashed tampering, because the existing tampering test
  covers malformed identity payloads but not a valid-looking unauthorized
  subset (`tests/test_worker_loss_executor.py:236-255`).
