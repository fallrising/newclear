### CLI and private-lifecycle audit

- Existing stdout is intentionally summarized: prepare emits `target_count`, execute emits `dissociated_count`, and recover emits `remaining_exact_count` (`labctl.py:899-942`). None of those success payloads directly serializes exact-ID arrays. The tests verify only one ID, so the redaction contract is narrower than the real multi-ID risk.
- The current private helper normalizes paths, requires them under project `private/`, rejects symlink components, constrains regular input size, rejects symlink record files, validates plan IDs and hashes, and writes immutably (`worker_loss_ops.py:17-82`). Existing tests exercise outside/symlink **input files** and a duplicate review plan, but not record-directory/file symlinks or the other plan categories.
- `prepare_execution_plan` re-derives the original review plan from the private input and checks its digest before saving a live execution plan (`worker_loss_ops.py:98-113`). This is a useful pattern for the new stages, but it does not bind a recovery journal, two fresh snapshots, or a replacement desired-spec revalidation.
- The only current mutation/recovery operations load `execution-plans` and invoke `WorkerLossExecutor`; recovery is read-only (`worker_loss_ops.py:116-128`). There is no route capable of turning `fresh_cleanup_plan_allowed` or `replacement_plan_allowed` into a new immutable plan.
- Generic lifecycle analogues in `tests/test_labctl.py` demonstrate no-replay, fresh-plan adoption, and private/symlink patterns, but that module contains no worker-loss route tests; worker-loss CLI tests currently live in `test_worker_loss.py` and `test_worker_loss_executor.py`.
