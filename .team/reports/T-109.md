## Summary

### Outcome

The narrowest safe ERU-016 increment is one **local-only, immutable, non-executable `restore-control` review planner**. It consumes a full-keyspace snapshot that was already captured outside this slice, plus hash-bound capture/status/source-state attestations, and saves a private plan. It does not add a backup, isolation, restore, launch, reconciliation, or generation-commit executor.

The plan must always say:

- `operation: control-metadata-restore-review-plan`
- `mode: restore-control`
- `executable: false`
- `execution_implemented: false`
- `remote_mutation_performed: false`
- every stage `implemented: false`, `executable: false`, and `evidence_status: checks_not_performed`

This matches V10: stop mutations, retain workers, use an externally obtained snapshot, isolate old control, restore, reconcile node/workload/plugin state and HTTP, measure RPO/RTO, and make no application-volume claim (`docs/SDD.md:189,192`; `docs/TASKS.md:42`). It also follows etcd 3.6: `etcdctl snapshot save` creates the backup; `etcdutl snapshot status` checks it; `etcdutl snapshot restore` creates new data directories and rewrites member/cluster identity; explicit membership and a new cluster token prevent old members joining; revision bump plus mark-compacted protects watch/cache consumers ([official etcd 3.6 disaster recovery](https://etcd.io/docs/v3.6/op-guide/recovery/); `docs/RUNBOOK.md:169-193`).

### Minimal private input schema

The v1 input is an exact-field JSON object; unknown/missing fields are invalid:

```text
schema_version: 1
mode: "restore-control"
topology_profile: "profile-a-four-host-basic"
expected_cluster: {cluster_id, generation}
controller_report: {path, sha256}
inventory: {path, sha256}
cluster_record: {path, sha256}
source_cluster_snapshot: {path, sha256}
snapshot:
  {path, sha256, size_bytes, capture_method, full_keyspace,
   capture_started_at, capture_completed_at, source_endpoint_evidence,
   status_evidence, toolchain, external_copy}
writer_quiescence:
  {confirmed, quiesced_at, in_flight_zero, writer_set_sha256, evidence_sha256}
old_control_plane:
  {source_member_set_sha256, source_cluster_id_sha256,
   source_token_sha256, source_data_dirs_sha256,
   isolation_confirmed, isolated_at, evidence_sha256}
target_etcd:
  {members, initial_cluster_sha256, target_token_sha256,
   target_data_dirs_sha256}
revision_policy:
  {mode, bump_revision, mark_compacted, basis_sha256,
   client_restart_set_sha256}
retained_workers:
  {worker_count, inventory_sha256, runtime_snapshot_sha256,
   node_workload_snapshot_sha256, plugin_accounting_sha256}
reconciliation:
  {expected_membership_sha256, expected_runtime_sha256,
   expected_plugin_accounting_sha256, expected_http_sha256,
   core_key_recovery_mode, core_key_evidence_sha256}
objectives:
  {rpo_candidate_seconds, outage_cutoff_at, protected_through_at,
   rto_candidate_seconds, rto_start_definition, rto_end_definition}
evidence_store:
  {available, encrypted, retention_policy_sha256, evidence_sha256}
```

Exact nested rules:

- `snapshot.capture_method` is exactly `etcdctl-snapshot-save`; `full_keyspace` is exactly `true`. A copied `member/snap/db`, prefix export, `/eru`-only export, or `--skip-hash-check` is invalid in v1. A copied DB can omit WAL updates and lacks the integrity hash the official restore flow expects.
- `snapshot.status_evidence` is `{path, sha256, snapshot_hash, revision, total_keys, total_size}` produced by a same-release `etcdutl snapshot status`; its parsed values are bound into the plan. The planner streams the snapshot file SHA-256 locally but does not invoke `etcdutl`.
- `snapshot.toolchain` binds one exact etcd 3.6 patch release and the locked release archive SHA-256 plus extracted `etcd`, `etcdctl`, and `etcdutl` binary SHA-256 values. Capture uses the bound `etcdctl`; future status/restore uses the bound same-release `etcdutl`; target `etcd` is the same patch unless a separately reviewed compatibility decision exists.
- `snapshot.external_copy` is `{object_id_sha256, object_sha256, encrypted, retained_until, restore_read_test_evidence_sha256}`. The object digest must equal local snapshot digest; plaintext URL/credentials are forbidden.
- Chronology is strict: writer quiescence and zero in-flight work precede capture start; capture completion precedes external-copy verification; old-control isolation follows capture and precedes any future new-cluster start. All timestamps are timezone-aware and within a bounded review window.
- `target_etcd.members` is the exact reviewed Profile A restore membership. Each item binds member name, host identity digest, peer/client URL digests, and new data-dir digest. Names/URLs/data dirs are unique; new directories cannot equal live old directories. `target_token_sha256` must differ from the source token. Do not store token plaintext in the plan.
- `revision_policy.mode` is `bump-and-mark-compacted`, with positive reviewed `bump_revision`, `mark_compacted: true`, a calculation/evidence digest, and every known Eru core/plugin/agent watcher in the restart set. Do not hard-code the upstream example bump as a universal value. If consumer behavior or a safe bump is unknown, save a blocked plan.
- `core_key_recovery_mode` is either `restore-verified-external-key` or `rotate-workers-and-revoke-old`; it must not silently reuse an unavailable key (`docs/SDD.md:168`).
- `objectives.rpo_candidate_seconds` is exactly 900 and `rto_candidate_seconds` exactly 1800. Actual RPO is later recorded as `outage_cutoff_at - protected_through_at`; never derive wall time from an etcd revision. Actual RTO starts at mutation-pause/outage declaration and ends only after reconciliation, HTTP success, and safe writer resume.

### Immutable plan fields

Normalize the input into an envelope `{plan, sha256}`. In addition to the normalized fields above, the plan binds:

- `id`, `created_at`, `operation`, `mode`, `topology_profile`, `cluster_id`, `generation_before`, `generation_after`;
- source commit/cleanliness, `code_inputs_sha256`, artifact/upstream/core-validation lock digests, and every private input `{path, sha256}`;
- snapshot file digest/size, capture/status values, toolchain digests, source endpoint/member/cluster identity digests, full-keyspace flag, external-copy digest/retention proof;
- source `membership()` digest plus complete retained-worker host/runtime, workload, node-resource, and plugin-accounting digests;
- writer-set/quiescence evidence, old-control identity/isolation evidence, exact target membership/data-dir/token digests, revision policy, client restart set, core-key policy, reconciliation expectations, evidence policy, and RPO/RTO definitions;
- `decision`, sorted `blockers`, immutable ordered stages, `checks_not_performed`, and the three permanent non-execution flags.

The source cluster snapshot must include node/workload/plugin details, not merely a count. The full raw record remains private; normalized digests and safe counts may be public. Snapshot integrity proves bytes, not semantic coverage, so the capture method and source-state evidence are separate bindings.

### Invalid versus blocked

Raise without writing a plan for malformed or unsafe input: schema/unknown fields, duplicate JSON keys/non-finite numbers, path escape/nested symlink/non-regular or oversized manifest, SHA mismatch, wrong cluster/profile/generation, drift during planning, non-full capture method, missing/invalid snapshot status, digest/status mismatch, copied DB/skip-hash-check, incompatible tool versions, duplicate/unsafe membership, reused token/data directory, fresh-mode fields, impossible timestamps, invalid RPO/RTO definition, or secrets in public fields.

Save an immutable **blocked** plan for a structurally valid scope whose prerequisite is false or unproven: controller not ready, tool binary integrity unavailable, writer set incomplete or not quiesced, in-flight operations nonzero, external encrypted copy/read test absent, old control not yet isolated, revision policy unresolved, core-key recovery unavailable, retained-worker snapshots stale/inconsistent, evidence store unavailable, or candidate RPO/RTO already missed. `decision: reviewable` means only that the future operation is sufficiently specified; it never makes the plan executable.

### Stage order and exact boundary

Observed/pre-boundary facts are validated in this order:

1. Bind controller/source/locks, exact inventory, cluster identity, and `generation_before`; reserve `generation_after`.
2. Bind writer-set and source node/workload/plugin/worker-runtime snapshot; verify quiescence chronology.
3. Locally hash the already captured full snapshot and validate supplied capture/status/tool/external-copy evidence.
4. Bind old-control isolation, target membership/token/data directories, revision/client-restart policy, core-key policy, reconciliation expectations, and RPO/RTO definitions.
5. Write exactly one private immutable review-plan envelope and print only the redacted summary.

**The slice ends here.** It must not call or render executable argv for `etcdctl snapshot save`, `etcdutl snapshot status`, `etcdutl snapshot restore`, SSH, service stop/start, firewall, copy/download, key rotation, reconciliation, writer resume, or generation commit.

The plan may describe, but never perform, these future stages in order: `writers-quiesced` -> `full-snapshot-captured` -> `external-copy-verified` -> `old-control-isolated` -> `target-generation-consumed` -> `new-data-dirs-prepared` -> `snapshot-restored-to-all-members` -> `restore-config-written-before-start` -> `new-cluster-started-and-healthy` -> `clients-restarted` -> `metadata-runtime-plugin-reconciled` -> `http-verified` -> `generation-accepted` -> `writers-resumed`. Every future stage requires fresh evidence; failure/uncertainty stops and reconciles read-only, never blindly replays.

### Fresh/restore separation and public redaction

Restore retains the three worker hosts and runtime, imports one complete etcd snapshot, creates new etcd cluster/member identities, and reconciles metadata against runtime. Fresh erases/reimages all hosts, starts empty etcd, replays desired apps, treats old metadata/runtime/plugin state as residue, and requires three independent successes. Neither builder, input directory, operation name, stage list, acceptance record, nor executor may be shared (`docs/M3-FRESH-REBUILD-PREP-2026-09-27.md:31,38-42`).

Public stdout is limited to plan ID/hash, operation/mode, decision, blocker count/category, `G -> G+1`, snapshot age/RPO status, and member/retained-worker counts. It must not include private/absolute paths, IPs/endpoints, aliases, provider/member/workload IDs, token or token digest, data dirs, snapshot/status output, key material, external object location, commands, app specs, or raw evidence. This follows the established count/digest-only convention (`docs/M3-FRESH-REBUILD-PREP-2026-09-27.md:17,46`).

## Risks and Follow-ups

- Highest risk: stale old members or writers can join/write around the restored cluster, causing split brain. Require externally verified writer quiescence, exact old member isolation, a new token, new data dirs, and no writer resume until final acceptance.
- A successful file hash/status does not prove intended keyspace semantics. Require `etcdctl snapshot save`, bind source revision/key count and a complete source node/workload/plugin inventory, then reconcile the restored metadata with retained runtime.
- Revision rollback can leave watchers/caches silently stale. Fail closed on an unresolved bump/mark-compacted policy and restart all known clients after restore.
- The quickstart lacks `etcdutl` installation and restore-mode/config ordering. Binary integrity and config-before-start are blockers, not later cleanup items.
- Retained workers can contain orphan or extra runtime relative to restored metadata; never deploy/remove or run blanket resource repair during reconciliation. Differences require exact-ID manual review/fresh plans.
- Core key loss can strand workers or preserve compromised access. Bind an encrypted external key proof or an explicit rotate-and-revoke path before reviewability.
- A restored etcd cluster protects control metadata only. It does not back up application volumes or business data (`docs/SDD.md:144,192`).
- Real V10 remains unverified until a separately reviewed executor/recovery design and an authorized VPS drill produce immutable command exits, versions, before/after resources, HTTP, journal, RPO, and RTO evidence. This report makes no completion claim for ERU-016/V10.
