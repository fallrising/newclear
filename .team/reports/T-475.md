### F-01 — P1: Git status may execute repository filters during offline preflight

`reading/trial.ts` initial `checkout()` line 76 invokes `git status` before checking repository attributes. The shared Git helper disables global attributes, hooks, fsmonitor and signing, but repository `.gitattributes` and common-Git `info/attributes` still select configured clean/process filters. Git's worktree/index comparison can invoke those filters, including commands that contact a remote or read unrelated data. The offline/no-content-execution promise therefore does not follow from avoiding an explicit `fetch` command.

The existing exporter already recognizes this boundary: it inspects cached, untracked and ignored attribute paths and nonempty `info/attributes` before `assertClean`. Apply equivalent protection to **both** content and export checkout preflight before `status`. Required regression: a synthetic configured filter must never execute, including ignored/untracked attribute cases; retain actual RED before GREEN.

### F-02 — P1: Partial/promisor checkout can implicitly fetch missing objects

Preflight calls `blob()` for the pinned registry, which uses `git ls-tree` and `git cat-file`. Neither the preflight nor the shared Git helper excludes partial/promisor clones or disables lazy object retrieval. A partial clone may have the commit but lack its tree/registry blob; object access can then trigger Git's automatic promisor-remote fetch. This contradicts the advertised offline boundary even after F-01 is corrected.

Reject local partial/promisor clone configuration before accessing missing objects, or explicitly prevent lazy fetch using a supported, verified mechanism. A regression should establish that an otherwise configured source cannot cause remote transport during offline preflight. This review identified the call path statically; it did not run a remote or synthetic transport probe.

### F-03 — P2: First deployment has a token-issuance dependency cycle

`PRIVATE-TRIAL.md` initially requires an existing dedicated token file before prepare, but formal wiring creates that token only after deploying the new Worker. The background explicitly leaves formal phase-2 wiring unperformed; an existing deployment need not have the token-issuance endpoint. The preparation command additionally rejects a zero-byte credential file, so an empty bootstrap file would not solve the sequence.

Document a deliberate owner-only bootstrap path, or separate artifact-preparation credential requirements: a nonempty inert sentinel that **does not match the exporter token format** can satisfy metadata-only preparation without pretending to be a valid credential. Keep export and scheduling prohibited until operator issuance replaces it and the real one-shot/remote-ACK checks pass. This is an instruction for later owner work, never evidence that owner authorization or formal credential acceptance occurred.
