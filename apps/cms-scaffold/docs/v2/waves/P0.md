## 目的與邊界

個人內容管理與相簿為預設驗收場景，核心對其他內容類型同樣適用。先避免寫入一半、重疊請求覆蓋、表單無法清空或送錯型別。無新增執行期依賴、無 schema migration、無 API 路徑新增；不提前實作 BW1a 的能力查詢、W1 的完整編輯器、模型設計器、會員功能。既有 BW1a 以後施工圖中整檔取代範例必須重新套用，不能覆蓋本波的可靠性修正。

## P0-DATA 契約

- Entry create、patch、publish、unpublish、archive、restore、softDelete、revert、purge 的資料庫變更，包含該操作的關聯、媒體附著、revision、audit，必須在同一資料庫交易內成功或全部回滾。僅涵蓋資料庫寫入；檔案上傳補償另列後續工作。
- 更新使用 store 層原子 compare-and-set，以讀到的 version 為條件；成功每次將 version 增一（無變更 publish 可維持 idempotent）。同版本競爭只允許一方成功，另一方回既有 409 VERSION_CONFLICT；不得以 JVM 全域鎖代替資料庫競爭保護。
- 狀態操作本波不增加 HTTP version 參數：以服務讀到的資料庫快照 version 做 CAS，保護讀寫間競爭；不宣稱能偵測使用者在很久以前開頁所形成的陳舊操作意圖。要求用戶端帶版本與 428 的端點契約留給 BW1c。
- 現有 PATCH version 可省略的相容性維持；提供舊 version 仍回 409。強制 428 仍由 BW1c 擁有。
- 還原 revision 需一起重新建立 refs／media attachments；失敗回滾。所有現存公開／權限規則維持，禁以改測試掩蓋行為。
- 發布媒體快照隔離：published Entry 的 attachment 索引保留工作副本與 publishedPayload 的聯集（同 media/field 去重），但公開讀取必須精確比對 publishedPayload 中同欄位的 mediaId，且類型啟用。草稿改成 B 圖時，原已發布 A 圖仍公開、B 不公開；發布後才切換。publish／unpublish／archive／revert 一起同步 attachment，且交易失敗全部回滾。
- JDBC 與記憶體 store 共同測 compare-and-set 語義；PostgreSQL 整合測試驗證真實回滾與競爭。Spring 無資料庫的 test profile 仍須可執行。

## P0-FORM 契約

- 已有欄位清空要以明確 null（或文字欄位允許的空字串）送出，不能省略而保留舊值。未填的新欄位可省略。
- 清空既有欄位統一送 null；草稿允許 required 欄位暫空，publish 仍由既有 required 驗證拒絕。此規則不放寬發布驗證。
- boolean 用可操作的三態控制（未設定／是／否），傳 JSON boolean/null；int 只接受 JavaScript 安全範圍內的有限整數，避免大整數被 Number 靜默捨入，非法內容留在表單並顯示可理解的錯誤；enum 提供既有 enumValues 選項。ref/media-ref 維持 UUID 介面，完整 picker 待 W1/W2。
- 儲存或狀態操作進行時禁止同表單重疊寫入。表單有未儲存變更時，狀態操作停用並提示先儲存；成功狀態操作後，顯示值與編輯版本一併同步回傳的工作副本，不能只前進版本而保留陳舊值。衝突失敗保留本地输入，告知先重新載入再重試，不自動覆寫。補清楚的錯誤／成功訊息與無障礙 label。
- 未授權發布規則維持；不以角色 UI 代替伺服器授權。只修改 Back entries 表單與必要 copy、對應測試，不重新設計 Front。

## shadcn-admin 參考

參考 `https://github.com/satnaing/shadcn-admin`（MIT，2026-10-03 查閱），採側欄資訊分組、頁標題＋主要操作、列表／詳細頁分離、表單區塊與狀態回饋、手機 Sheet 與鍵盤操作模式。沿用 packages/ui 的 shadcn/ui、tokens、React Router 與既有 session，不導入 Clerk、TanStack Router、模板商業指標或整包依賴。直接複製上游程式碼時才需保留其 LICENSE／來源；本波只參考模式。

Back 優先完成內容操作；Admin 只管模型、帳號與治理；Front 公開呈現。shadcn-admin 是工作介面補充參考，既有 Shopify 參考中不衝突的互動規則保留。P0 不宣稱完整視覺改版完成。

## 驗收與測試先行

1. 寫入 Entry 後讓附著更新失敗：Entry、refs 均無部分提交。
2. 同 version 的兩次寫入：一成功、一衝突，資料與 version 不被覆蓋；狀態操作與 patch 也受此條件保護。
3. revision 還原後 refs／attachments 與工作副本相符；發布快照保持原契約。
4. 表單清除已填欄位、boolean false、合法整數、非法整數、enum 與 409 保留輸入。
5. 已發布媒體 A 改為工作副本 B：發布前 A 可公開、B 不可；發布後反轉；revision 還原仍不提前公開。停用類型不能公開媒體。
6. 先看到針對缺陷的紅燈，再實作。文件／參考整理不新增機械式測試。

命令（在 apps/cms-scaffold）：`./gradlew test`、`./gradlew integrationTest`（JDK25＋Docker PostgreSQL16）；`npm run lint`、`npm run typecheck`、`npm test`、`npm run build`、`npm run test:bundle`、`npm run e2e:mock`。與本波無關的基線失敗要保留原因，不能標通過。

## 個人生產使用的剩餘門檻

既有資料注意：本波沒有 migration 或全量重建 attachment 索引。歷史上已遺漏發布媒體關聯的 dirty published entry，需要後續內容異動重建聯集，正式升級前應盤點／修復；新的公開授權檢查立即阻止未發布媒體曝光。

本波完成也不等於 production-ready。尚需獨立施工圖：正式管理員/權限初始化、移除 demo seed 的正式生命週期、HTTPS 與靜態檔案 serving、安全埠與秘密注入、PostgreSQL＋媒體的一致備份／還原演練、媒體檔案失敗補償、升級與回滾。不得對正式資料執行 README 的 `down -v`。部署與外部變更需另有使用者授權。

動態類型導覽／metadata／capabilities 沿 BW1a；查詢沿 BW1b；完整表单／列表沿 W1；管理模型沿 BW6/W6，不能在狀態表中將規格當成功能。
