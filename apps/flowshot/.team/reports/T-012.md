The first hot spot is **not** the GFM table extension's separate EditMap class. Sample stack is `buildModel → remark parser/fromMarkdown → micromark document.writeToChild → EditMap.consume`. Inspected pinned micromark 4.0.3 `lib/initialize/document.js`: lazy-line repair queues two edits then consumes the accumulated `self.events`. In micromark-util-edit-map 1.0.0, `consume` slices edited suffixes, truncates the array, then also copies the entire unchanged prefix, clears the original and pushes everything back. Repeating this repair as document history grows can cause superlinear aggregate copying. The source supports this hypothesis and the profile locates its cost; one profile does not establish a measured scaling exponent or call count. The package already uses a Map to avoid quadratic lookup in `add`; another lookup-index change would miss this dominant copying path.

Second stack: `rehypeRaw/hast-util-raw → parse5.getFragment → _adoptNodes → defaultTreeAdapter.detachNode`. Inspected the nested 7.3.0 parser and adapter, rather than unrelated top-level parse5 8.0.1. Fragment adoption repeatedly detaches children; `detachNode` uses `indexOf` plus `splice`, which shifts remaining siblings. Repeated front removal over a wide fragment is an additional superlinear-work candidate. Allocation/copying plausibly contributes to GC, but this profile cannot attribute all GC to either function.
