## Option A: TUI with incremental streaming

Implement an explicit TUI execution transport on Unix using existing libc/PTTY primitives, with mode recorded in diagnostics. Preserve existing print mode as an explicit selection; a selected TUI mode fails closed rather than silently becoming print. Use only owned work/session/tap files, strict MCP tool allowlist and unchanged official auth flow; no credential extraction, entrypoint spoofing, TLS/proxy manipulation or permission bypass. The implementation would use an audited minimal response tap, not import arbitrary upstream code or install a dependency. Tap absent/incompatible must produce a clear failure rather than fabricated streaming success. This proposed fail-closed behavior is stricter than magpie, which falls back to complete-message transcript output when its tap is unavailable. Necessary scope includes subprocess cancellation/cleanup, structured message/tool/usage fidelity and no duplicate transcript/tap events. This requires owner acceptance of runtime preload instrumentation because it changes the previous no-injection design and account-risk tradeoff. Offline tests do not establish subscription savings or account acceptance. Estimated implementation/review/delivery90–150active minutes after design approval, with20minute checkpoints.

## Option B: TUI without preload

PTY plus owned session transcript, no Bun/network hook. Structured complete messages/tools/usage could be reconstructed after transcript writes. This loses true incremental token streaming: sending a whole completed message as an SSE chunk does not satisfy the existing streaming claim. Requires explicit acceptance of that product limitation; it is not a drop-in core replacement. Comparable lifecycle work still needed; estimated60–100active minutes. Terminal-screen scraping is not offered as a reliable substitute for protocol events.

## Option C: Keep the documented print transport while diagnosing proven gaps

Keep existing streaming/tool behavior and the official programmatic route. Separately bound an offline diagnosis of the previously observed native reuse gap and inspect prompt/cache stability; change runtime only if evidence establishes a defect. This does not solve a possible provider-side subscription weighting difference and cannot promise savings. Estimated diagnosis20–35active minutes before deciding a concrete fix; no live calls.

Recommendation under the owner's earlier account-risk priority: C until A's instrumentation tradeoff is explicitly accepted. The user explicitly requested TUI, so the project will not silently substitute C or weaken streaming under B. While this decision is pending, other-CLI research and review continue. ### Mechanisms and bounded actions

1. Process reuse avoids startup and can retain live state. Native session resume restores saved conversation. Prompt caching reuses a matching server-side prefix. Subscription accounting converts work into a provider-specific allowance. None is a synonym for another; context continuation also does not prove native reuse.
2. `PROVIDERS.md` plus `providers.rs` confirms Claude/Cursor are the native CLI routes. SIWC/Grok/OpenCode/Antigravity are HTTP routes. No new integrations follow from this survey.
3. SIWC already generates a deterministic key from model/instructions/first input when a client key is absent (`prompt_cache.rs:15`), and adds matching session/thread headers (`:48`); `proxy.rs:407` scopes this generation to SIWC. This is a routing attempt, not a cache-hit guarantee. Keep existing stable-prefix/key contracts; do not claim a numerical saving.
4. Cursor is the only other existing native CLI candidate for a future controlled comparison. Its raw result cache buckets should be retained separately from normalized totals; no current evidence warrants a TUI change, a new runtime RED, or new paid calls.
5. Grok stable-key routing and OpenCode proxy cache compatibility are evidence-backed questions for future authorized, endpoint-specific work. They are not demonstrated thinrouter product defects. Do not alter Grok auth/endpoint, restore codex credential reuse, or expand wishlist integrations on this basis.
