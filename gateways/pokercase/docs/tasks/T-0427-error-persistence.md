## Source and design before reproduction

HTTP `forward_chat_completions_inner` owns the response diagnostic body and puts it into `UpstreamAttemptError`; conversions/provider preparation and transport errors use the same object. All three handler failure branches write a truncated body to `Store::log_usage` before returning it or selecting fallback. CLI start/collect errors go through `record_failure`, the fourth error write entry. Success paths pass error None. `Store::log_usage` is the only usage_events insertion function; `recent_usage` feeds admin JSON, the web usage page and TUI, and `usage_csv` exports the same error. Escaping/truncation is not de-identification. Failure status and retryable govern existing cooldown/fallback independently of body contents; per-target Instant starts remain inside target loops.

First demonstrate the canary reaching SQLite and its read surfaces on the unchanged baseline. If reproduced, keep arbitrary diagnostic text out at the error-write boundary using a fixed application-owned classification, preserving separate numeric status, timing, row count, retryability, cooldown and caller-facing error behavior. Avoid regex secret guessing, body parsing, schema changes, new diagnostics or retroactive historical cleanup. Decide the exact minimal code change only after the RED evidence. Request metadata (configured model/connection names), caller-facing inference errors and legacy rows retain their existing contracts; this slice does not promise whole-database anonymization or new terminal accounting.

## Local reproduction and correction

The test messages list surfaces only; captured runtime logs were scanned and did not trigger the marker assertion. This proves synthetic persistence, not an observed real credential disclosure.

The minimal fix sends all three HTTP failure branches through the existing CLI `record_failure` and replaces the persisted diagnostic with `upstream_attempt_failed`. Numeric status remains separate; the body remains in the existing caller response only. No schema/migration, historical-row cleanup, token/cost semantics, fallback/retry rules or new diagnostics.
