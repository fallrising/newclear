## 3. 目前不能直接 make up 的原因

### 安裝權限

`sudo -n true` 失敗。`sudo -n -l` 顯示 g1ops 的免密權限只涵蓋 root-owned `onevps-hostctl` 的固定 operation，包括 access status／audit、baseline preflight／plan／validate 及綁定 digest 的 baseline apply／repair。這不是 apt、檔案安裝、systemctl 或通用 Ansible become 權限。

現有 helper 沒有 ERU install operation，不能把 baseline-apply 當成任意安裝入口。未嘗試修改 helper、加 docker group、chmod runtime socket 或放寬 sudoers。

### 長期 runtime 權限是另一件事

OneVPS 已驗證 SSH policy 為 `PermitRootLogin no`；原 quickstart 會安裝允許 root key login 的 SSH drop-in。本案不能把 root SSH exception 當作 routine 安裝細節。

core 透過 SSH 直接轉送 containerd Unix socket，並執行目錄建立、部分 snapshot mount 與 journalctl 等操作；它不會自動使用 g1ops 的 `sudo` allowlist。因此取得一次性安裝權限，或只把 `eru_ssh_user` 改為 g1ops，都不代表 worker runtime 可用。

待決策路徑：在保留 OneVPS root-login 禁令的前提下實作／驗證專用 runtime 權限介面；或者由 owner 明確批准測試 worker 的局部 SSH policy exception。後者會影響 OneVPS 原有 access validation，必須另記錄範圍／撤銷方式，不能同時宣稱維持原基線。

### 現有 Docker／containerd

Docker unit 明確使用 `/run/containerd/containerd.sock`；containerd unit 執行 `/usr/bin/containerd`。上游 quickstart 會寫 `/etc/systemd/system/containerd.service` 並重啟同名服務，不能原封不動套用。

候選最小適配：保留既有 binary／unit／socket，不重啟 Docker 依賴，驗證 restart plugin／runtime 設定後讓 ERU 使用獨立 `eru` namespace。namespace 是管理分組，**不是安全邊界**。所有 cleanup 只能作用在本專案已記錄的 Eru workload IDs。

若要求獨立 containerd daemon，需另外處理 root/state/socket、runc PATH、agent、CNI 與 core 硬編碼 `/var/lib/containerd` 的容量探測；目前沒有可直接套用的 overlay。

最初以 g1ops 執行 `docker ps` 權限不足；後續透過 ckc + sudo 讀取 `docker ps -a`，四台皆無容器，現有 containerd namespace 僅 moby。這不授權清除現有 volumes／網路。

### SSH alias 與 service address

B 必須使用現有 SSH aliases；etcd／core／agent 彼此應使用 Tailscale 位址。上游在多個模板直接用 inventory_hostname，且 core_host 同時拿來 delegation 與 API endpoint，需先拆分 transport host 與 service address。

core 的 Go SSH client 不會繼承 B 的 `~/.ssh/config`。它需要自己的 key 與 `ssh.known_hosts`；已核對 source 顯示空 known_hosts 會略過 host key 驗證。overlay 必須從既有可信 host key 記錄導出對應 private address 的 known_hosts，不能以未驗證的 keyscan 取代。

## 5. 可重跑的診斷

在 controller B 的專案目錄執行：

```bash
python3 scripts/preflight.py --output-dir private/preflight
python3 scripts/check-binaries.py --output-dir private/binary-checks
```

兩個工具預設依序處理四台，可用 `--host disposable-01` 限制單台。前者只收集診斷；後者會在 remote temporary directory 下載已鎖定的 archive、核對 bytes、執行 version command 並正常清除。任一 timeout 需檢查該次 evidence；不能假定異常中斷已完成清理。

每個命令輸出標明 alias。診斷工具 exit 0 只代表 evidence 收集成功；個別檢查（例如 Docker 權限）可以失敗。binary checker 另要求 6 個命令及 temporary cleanup 均成功。

原始 JSON、真實地址與下載 cache 放在 gitignored `private/`，檔案權限 0600；公開文件僅記錄別名與去識別的結果。這不是完整 `labctl`，不具備 apply／rebuild 功能。
