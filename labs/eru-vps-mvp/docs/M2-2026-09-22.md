### etcd 延遲與配額處理

01 的 etcd 日誌在 11:13–11:14 UTC 出現 `slow fdatasync`，包含 11.26、23.53、9.61 秒的同步耗時；其後 health／alarm 查詢亦有逾時。11:16 的 vmstat 取樣顯示 17–20% I/O wait，根磁碟使用約 1%、剩餘約 281 GiB，CPU 與記憶體並未飽和。這支持「當時有儲存 I/O 等待」的判斷，不能單憑這些資料確定是供應商共享儲存、宿主機或 guest 內的根因。

第一次失敗後留下恰好 1 CPU／256 MiB／1 GiB 的配置帳目。等 health 恢復，確認全群 workload list 空、worker-4 containers／tasks 空、占用量完全符合本次 evidence，才對 **worker-4 一台**執行 `node resource --fix`。沒有修改其他節點或 etcd keys。

修復後 CPU／memory／storage 全零，`node resource worker-4` 的 DIFFS 空。第一次核對因 `cpu_map` 從 `{0:0,1:0}` 變成空 map 而觸發 JSON 全等斷言；保留該錯誤紀錄，再以唯讀資料確認數值配額已回收。沒有因此再次執行 fix，也没有把它加入自動重试。

最後一次執行前檢查仍觀察到 etcd unhealthy，因此停止後續部署；短暫 health 通過不能證明問題已解決。

### core panic 與修補草案

11:22:05 UTC，core 的 stack trace 為 `panic: cannot create context from nil parent`，位置是 `cluster/calcium/lock.go:111`。systemd 於 11:22:11 自動重啟，觀察到 NRestarts=1；etcd 沒有被本輪操作重啟。

已核對固定來源：etcd lock 在取得鎖失敗時回傳 `(nil, err)`；`withNodesLocked` 直接把回傳的 context 指派回 `ctx`，返回錯誤時 deferred cleanup 又呼叫 `context.WithoutCancel(ctx)`，因此 panic。對照 [lock.go 固定來源](https://github.com/projecteru2/core/blob/e19ceb7e09d95bedea3eb0c25bec9308101fecc5/cluster/calcium/lock.go) 與 [etcd mutex 固定來源](https://github.com/projecteru2/core/blob/e19ceb7e09d95bedea3eb0c25bec9308101fecc5/lock/etcdlock/mutex.go)。

已準備 [修補草案](../patches/core-v0.1.5-lock-context.patch)：只有成功取得鎖後才更新 ctx，失敗時保留可供 cleanup 使用的原 context，並加入「Lock 回傳 nil/error 時不 panic」測試。`git apply --check` 與 gofmt 檢查通過；**尚未編譯或跑上游 Go 測試，也未部署**。B 本機 Go 是 1.22.2，上游 module 要求 1.27.0，仍需準備對應建置環境、跑回歸並產生新 artifact checksum。這個修補不會解決底層 I/O 延遲。
