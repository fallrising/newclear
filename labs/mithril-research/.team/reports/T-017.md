## Summary

DESIGN recommendation: implement only a separate, local durable bootstrap intent/uncertainty journal. Root must freeze this contract before builder work. The useful guarantee is cooperative fencing on the **same retained journal root**: persist one exact original action as uncertain before any caller could dispatch it, and refuse every subsequent reservation. No current observation, new approval, timeout, opposite state, or late effect clears that uncertainty. This task implements no behavior and changes no existing contract.

### D1 — Scope, APIs, and authority

Add only `scripts/bootstrap_journal.py` and its focused `tests/test_bootstrap_journal.py`, with Python 3.11 standard library dependencies. Recommended exact public APIs are:

```python
initialize_journal(plan, expected_bootstrap_digest, state_root)
journal_status(plan, expected_bootstrap_digest, state_root)
record_intent(plan, expected_bootstrap_digest, state_root, phase_id, action_index)
```

Each returns the detached JSON-compatible result defined in D3. Inputs are never mutated; returned nested objects cannot mutate retained state or the caller's plan. `initialize_journal` creates an entirely new root; it is deliberately not idempotent. `journal_status` and `record_intent` require an already initialized root and never create directories, lock files, or metadata. All three acquire the same exclusive nonblocking OS lock, including status. No dispatcher, transport, collector, runtime, approval, clock, callback, or effects argument exists. No `mark`, resolve, complete, reset, adopt, abandon, retry, or phase-advance API exists.

One successful `record_intent` changes local state from `no-intent` to `uncertain`. The uncertainty is conservative from the first durable record: an effect may or may not have happened. A separate intent-recorded state would add a transition without giving this library a way to prove dispatch absence. A `no-intent` status means only that this validated local root contains no committed intent; it does not prove remote absence or grant safe retry. No result is phase admission, authentication, ownership authority, freshness, or permission to execute.

This journal may reserve **any one** exact action selected from the original plan. It does not enforce phase order, readiness, barriers, action sequencing, or successful earlier effects. This is an explicit boundary, not an executor. Keep P1a/P1b journals, P1c proposal validation, P1d collection, P1e predicates, all existing files/contracts, and both locks unchanged. In particular, do not alter old uncertainty resolution behavior as part of this slice.

### D2 — Original plan and exact action binding

Every API validates an independently supplied lowercase 64-hex `expected_bootstrap_digest` using unchanged `bootstrap.validate_bootstrap_plan`. Do not recover this independent expectation from either journal or plan. Require the derived original plan's classification to be `pristine`; the already-converged zero-action proposal is refused by all three APIs. The validated original has four exact phases and 17 exact actions. Revalidation reconstructs the original source manifest, ownership, expected six node IDs, observations, phase requirements, and actions. The unkeyed digest detects mismatch; it does not authenticate any of them.

Use `type(phase_id) is str` and exact equality to an original `phase_id`; use `type(action_index) is int` with `0 <= action_index < len(selected_phase["actions"])`. Bool, negative/out-of-range indexes, arbitrary kinds, changed targets, and caller-provided action dictionaries are refused. Derive and deep-copy the action from that phase, retaining every original field, including host/role/container/node identity, epoch, peer endpoint, slot range, or replication master ID as applicable. No new action normalization or independently editable action schema is introduced.

Every state read compares metadata to fresh derivation from the supplied original plan: bootstrap digest; ownership `run_id`, `plan_sha256`, `bundle_sha256`; complete original `ownership`; complete `expected_node_ids`; and `observations.origin`. Thus the full digest binds the original machine identities, labels, network/storage specification, original observations, actions, and phase requirements even though the large original plan is not duplicated in the journal. Reject any binding change, synthetic/operator-origin change, wrong six-node mapping, or recomputed foreign proposal. A changed approved snapshot or digest cannot reopen a retained root.

### D3 — Exact state and return schemas

All objects have exact key sets; unknown keys/statuses/versions are refused. Common flags, named `FLAGS` below, are exactly:

```json
{"lane":"offline-bootstrap-journal","execution_supported":false,"live_ready":false,"live_runtime":"UNEXECUTED","effect_dispatch_supported":false,"resolution_supported":false}
```

Immutable `journal.json` metadata has exactly these fields:

```text
schema_version = 1 (strict int)
all six FLAGS fields, exactly as above
journal_id = uuid4().hex, lowercase 32 hex
bootstrap_sha256 = independently validated original digest
run_id, plan_sha256, bundle_sha256 = exact validated ownership values
ownership = deep copy of complete validated original ownership
expected_node_ids = deep copy of complete validated original six-role map
source_origin = exact validated original observations.origin
root_binding = {device: root st_dev, inode: root st_ino}
lock_binding = {device: permanent lock st_dev, inode: permanent lock st_ino}
```

Both identity objects have only `device` and `inode`; values are strict integers with device nonnegative and inode positive. Bind to actual open descriptors and current path identities. There are no timestamps, raw observations, credentials, caller assertions, approval references, or mutable counters.

The optional immutable `intent.json` has exactly:

```text
schema_version = 1 (strict int)
journal_id = exact metadata journal_id
bootstrap_sha256 = exact metadata bootstrap_sha256
intent_id = fresh uuid4().hex, lowercase 32 hex
status = "uncertain"
phase_id = exact original selected phase_id
action_index = strict original selected zero-based index
action = deep copy of that exact original action
```

Validate complete metadata and intent semantics on every open. Do not trust a self-consistent hash, UUID, or action copied into a different journal. No intent file is the sole valid `no-intent` representation; `null`, empty/truncated JSON, a directory, or an unknown filename is never absence. Once an intent exists, every `record_intent` refuses, including identical action/digest/index, another action, and a new process invocation. Status still returns `uncertain`; there is no successful duplicate acknowledgment that could prompt another effect.

Each API result has exactly `{schema_version: 1, **FLAGS, journal_state, metadata, intent}`. `journal_state` is `no-intent` iff `intent` is null and otherwise `uncertain`; `metadata` and `intent` are the fully validated detached objects above. Initialization returns `no-intent`; recording returns `uncertain` only after the durable commit and postcommit checks. No `healthy`, `safe_to_retry`, `executed`, `completed`, `cancelled`, authority, or remote-readiness result exists.

### D4 — Private paths, bounds, and CLI

`state_root` must be a plain string. Reject its raw spelling **before** constructing/normalizing `Path`: require an absolute single-root spelling, no NUL, no `..` components, no dot components, repeated separators, trailing separator, or double-leading slash; require raw equality with both its `Path` string and `normpath`. Root `/` itself is refused. Traverse every component using no-follow directory descriptors; do not rely on a final `resolve` or lexical prefix test. Require outside the source tree, and reject either ancestry overlap with every manifest host `data_root`. Do not permit a journal inside a data directory or a journal root containing one. Root and existing immediate parent are owned by the current UID and exactly mode 0700. Parent directories are never created. This stricter new profile does not change old loaders or their compatibility.

Existing regular journal files are current-UID-owned, exactly 0600, one hardlink, non-symlinks; `.lock` additionally has exact zero length. Use no-follow/nonblocking opens and fstat before reads so FIFO/device/socket inputs cannot block. Compare fstat and no-follow directory entries, reject type/identity/size changes, read at most bound+1, and fail on growth. Each metadata/intent file is bounded to **65,536 bytes including its terminal LF** and must equal canonical ASCII JSON plus one LF. Exact numeric types, duplicate keys, NaN/Infinity, invalid UTF-8, malformed JSON, recursive/excessively nested values, and invalid nested shapes are refused with `LabError`, never interpreted as absent. Canonicalization failures are normalized at the API boundary. Pending files are refused without parsing them. Filesystem errors are sanitized; interruptions retain artifacts and propagate from APIs without cleanup.

The CLI original plan input is a private regular file of at most **1,048,576 bytes**, also bounded before parsing, with the same raw lexical/no-follow/owner/mode/link/source rules for its private parent and file. Its JSON accepts insignificant whitespace within that byte cap but rejects duplicate keys/nonfinite values/invalid UTF-8/nesting errors; unchanged bootstrap validation enforces the original canonical plan cap. Do not reuse an old loader that normalizes away rejected raw path aliases.

Exact CLI interface is:

```text
bootstrap_journal.py init --plan PATH --expected-bootstrap-digest HEX --state-root PATH
bootstrap_journal.py status --plan PATH --expected-bootstrap-digest HEX --state-root PATH
bootstrap_journal.py record-intent --plan PATH --expected-bootstrap-digest HEX --state-root PATH --phase-id PHASE --action-index INDEX
```

Disable argument abbreviation. CLI `INDEX` must match `0|[1-9][0-9]*` before bounded integer conversion; reject signs, spaces, leading zeros, and oversized integers. The API still requires strict int. No implicit init, optional output writer, execute/mock flag, credentials, approval, reset, resolution, or caller action input exists. Successful stdout is exactly `{**FLAGS, result: COMMAND, journal_state: STATE, intent_count: 0|1}` with exit 0. A truthful uncertain status is successful. All refusal and parse-error stdout is exactly `{**FLAGS, result: "error", error: "bootstrap-journal-refused"}` with exit 2, without path/value echo, traceback, or raw exception stderr. Help prints only `{**FLAGS, result: "help", actions: ["init", "status", "record-intent"]}` and exits 0. Summaries omit IDs/digests/targets/private paths. Internal API state is private; public docs/evidence contain deidentified summaries only.

### D5 — Root, locking, persistence, and crash windows

Initialization requires the requested root to be entirely nonexistent. Exclusive `mkdir(0700)` creates a permanent initialization marker; existing empty directories are refused rather than adopted. Fsync the parent after creation. Exclusively create the permanent empty `.lock` once with mode 0600, validate its descriptor/path identity, and acquire `flock(LOCK_EX|LOCK_NB)`. Never replace or remove this file. A partial root left by any failed initialization is retained and refused forever by this slice. Successful `journal.json` is the immutable initialized-state marker; a missing marker never means an empty journal.

Opening an existing root never uses `O_CREAT` for root/lock/metadata. Before and after locking, compare the root's descriptor to the no-follow parent entry and the lock descriptor to its entry. Validate persisted root and lock dev/inode, mode, ownership, type, and lock size. Repeat identity/namespace checks around commit and before every successful return while holding the lock. A copied root, substituted lock, removed lock, renamed/replaced root, or extra entry refuses. Reject a busy lock promptly; no waiting loop. Flock is cooperative exclusion on the same retained inode, not protection against an actively malicious same-UID process.

The only successful namespaces are `{.lock, journal.json}` and `{.lock, journal.json, intent.json}`. Reserved pending names are `.initialize.pending` and `.intent.pending`; either one, any unknown entry, or any missing required file causes refusal. Do not clean up unknown/pending entries automatically. Do not reuse `labctl.owned_scope` or `atomic_write`: the former can initialize/adopt older state and does not persist the lock identity; the latter removes a failed temporary file, losing the new conservative failure marker.

For both metadata initialization and intent creation: require absent final/pending destination; create the fixed pending file using exclusive no-follow creation at 0600; write the entire bounded canonical payload plus LF; flush and fsync that file; fsync the root directory so the staging entry is retained before rename; recheck root/lock/pending identity and absent final; atomically rename pending to its fixed final name; fsync root again; revalidate and reread complete state before successful return. Initialization additionally fsyncs the parent before returning. No finally/error handler unlinks pending, final, root, or lock. An exception after a rename may leave a valid committed intent even if the caller saw an error: later status may report uncertainty, but recording still refuses. Failure is not cancellation.

Crash categories must remain distinct: before root creation, there is no initialized journal; after root creation but before valid metadata, there is an unusable partial root; before intent staging, a complete initialized root may still report local `no-intent`; after staging, either retained pending blocks every API or committed intent yields uncertainty. If intent recording did not durably return success, a test caller must not invoke even its mock effect. After a successful return, external caller interruption, dispatch failure, lost response, or late work cannot change the journal's uncertainty. Lock release on process exit enables only status inspection, never replay.

Durability is conditional on local filesystem/OS support for successful file fsync, directory fsync, atomic rename, and cooperative locking. Unsupported operations fail closed. Process-kill/mock tests establish implementation ordering and interruption behavior, **not** actual power-loss proof. Preserve failed artifacts for investigation; no repair/recovery protocol is authorized. Fresh initialization at another path and same-UID rollback/removal cannot be prevented by an unkeyed hash/library. A new root is not authority to replay an earlier effect. Do not claim global exactly-once execution or fencing across roots/filesystems.

## Risks and Follow-ups

The library cannot authenticate operator assertions, establish remote outcomes, stop a caller bypassing it, prevent another root or same-UID rollback, or prove physical power-loss durability with process tests. Pending/partial roots intentionally have no automatic cleanup or recovery. Same-root cooperative lock and retained filesystem identity are the full fencing boundary. A useful future executor must explicitly consume this boundary without mistaking a successful reservation or local `no-intent` status for admission. No live readiness or deployment claim follows from this design.
