## 1. MVP 要回答的問題

兩種職業與一條短冒險路線，能否讓隔離角色透過原生瀏覽器完成採集、製作、交易及重複塔路，並在受控策略下持續流通補給且保持帳目正確？

2026-10-22 owner 明確接受「按你建議操作」：將 RE-3 改為自動化可玩性驗收。原本 2–3 位真人、30 分鐘、自發交易、訪談與願意再玩的門檻不再是本次必填項；這是 owner 指定的實驗問題變更，不是自動測試證明真人體驗。真人理解、動機、趣味、留存及長期平衡仍未驗證。詳見 [RE-3 契約](re3-contract.md) 與 issue #481。

## 2. 一場可觀察的故事

霧岸鎮外有礫坡（礦石）與潮林（藥草），兩區有來回路程，選路有機會成本。
鐵匠用礦石做「修補組」，藥師用藥草做「行路藥」；塔路上的路障需要修補組，戰鬥需要行路藥。
每人只能做自己專精的配方；初始補給耗盡後，出門前要向對方買缺的東西。
走完塔路得到一次性獎勵；回鎮後可以交換剩料，再走一次。

RE-0 初始背包假設：每個新角色僅獲一次異職成品，讓 RE-1 單人首輪能靠採集與自己的配方完成；重連與重啟不補發。每輪塔路消耗兩種成品，之後仍須向另一職業取得缺品。首輪是否交易與真人重玩動機仍未驗證，不以此規則宣稱已證明交易需求。

畫面：俯視格子地圖、角色、資源點、背包、交易列表、簡短訊息，用自有幾何圖形與文字。
只有試算表或表單不算可玩。

## 4. MVP 範圍

| 面向 | MVP |
| --- | --- |
| 世界 | 一座鎮、兩個採集區、一條塔路（一個路障、一場遭遇） |
| 角色 | 移動、生命值、背包、一個專精（開局選定） |
| 職業 | 鐵匠、藥師；採集人人可做 |
| 製作 | 每職業一個配方，無品質等級 |
| 交易 | 掛單：物品＋固定價格；另一人按「買」即完成。可取消自己的掛單 |
| 貨幣 | 開局固定補助＋塔路一次性獎勵；交易只轉移，不創造 |
| 遭遇 | 確定性規則：有行路藥則勝，否則退回；有修補組則過路障 |
| 同步 | 瀏覽器每 1–2 秒輪詢狀態 |
| 保存 | 每個動作後寫入 SQLite；重啟可續玩 |

不做：品質等級、製作委託單、escrow、訂單到期、拍賣、浮動價格、經驗值、公會、NPC 收購、LLM NPC、公網部署、正式登入。

## 5. 架構

- Python 3.11 標準庫 `http.server.HTTPServer`（**單執行緒**）＋ `sqlite3`；瀏覽器原生 HTML/CSS/JS。不加依賴。
- 單執行緒伺服器讓動作逐一處理，自然避免同時購買同一掛單的競爭；每個動作一個 SQLite transaction。
- 伺服器決定移動、採集、製作、交易與遭遇結果；瀏覽器只送意圖，不送金額或結果。
- 遊戲規則寫成純函式（輸入狀態＋動作 → 新狀態或拒絕原因），HTTP 與 SQLite 留在邊界，規則可單獨測試。
- 本機或區網試玩；玩家以名稱加入，伺服器發一個 token 綁定角色。不宣稱 production authentication。

## 6. 資料

| 表 | 欄位 |
| --- | --- |
| characters | id、name、token、x、y、hp、profession、coins、tower_stage（0／1／2）、tower_reward_claimed |
| items | character_id、item、quantity |
| listings（RE-2） | id、seller_id、item、quantity、price、status（open／sold／cancelled） |
| log | seq、character_id、action_id、action、status、result、time；角色＋action_id 唯一 |
| joins | join_id、payload、result；建角重試收據 |

數量與金額為非負整數。購買時在同一 transaction 檢查掛單仍 open、買家錢夠、賣家仍有物品，然後轉移並標 sold。
`tower_stage` 保存本輪路障／遭遇進度；回鎮歸零。`tower_reward_claimed` 是永久的一次性獎勵標記，與發獎一起提交。建角補給與角色一起建立，重啟不補發。細節見[規則表](rules.md)。
每個動作帶 client 產生的 `action_id`；RE-1 將原先「最近」明確化為每角色完整的持久收據歷史，包含規則拒絕。同 ID、同內容回傳原結果，不重複執行；同 ID、不同內容拒絕（409）。這讓穿插其他動作後才到達的延遲重試仍安全，重啟不失效。建角同樣用 `join_id` 防止重複發補給；收據與狀態一起提交。此本機原型不清理收據，資料庫會隨動作增長。HTTP／UI 邊界與回復流程見 [RE-1 契約](re1-contract.md)。

## 8. 驗收案例

- RE-A01（修訂）：不讀遊戲原始碼、路線文件或狀態 API 的 agent，僅依 UI 探索；記錄前五分鐘看到的目標／下一步、實際耗時、操作、卡點與截圖。不得將 agent 表現外推為新人理解。
- RE-A02（修訂）：兩個隔離瀏覽器角色完成採集→製作→交易→第二輪塔路及故障恢復；另以策略模擬核對多輪補給、貨幣與物品收支，公開停滯情境。
- RE-A03：同一 `action_id` 重送多次，物品與金額只變一次。
- RE-A04：兩人購買同一掛單，只有一人成功；失敗者錢不變。
- RE-A05：購買與取消同時發生，只有一方生效；全體貨幣總額＝補助＋獎勵總和。
- RE-A06：偽造 token、遠距採集、負數或超大數量、不存在物品，世界狀態不變。
- RE-A07：伺服器重啟後角色、背包、掛單與重啟前一致。

## 9. 自動化驗收記錄

三層證據分開標示：固定腳本瀏覽器旅程；沒有路線預告的 agent UI 探索；使用已知規則的受控策略模擬。門檻與指標見 [RE-3 契約](re3-contract.md)。保留失敗／卡點、操作數、時間與截圖；策略造成的交易必須稱為策略交易，不能稱為自發交易。

結論限於此本機實作與指定情境的可操作性、恢復能力與資源流通。真人訪談、樂趣、願不願再玩、經濟均衡與產品去留決定皆未驗證，不讓 agent 代答。
