# Retro Economy：霧岸鎮第一片

- 日期：2026-10-21。
- 狀態：Proposed；未實作、未建置、未試玩、未部署。
- 投入／文檔檔位：未分級。
- 本文的數值是待驗證起點，不是平衡結果。

## 1. 問題與玩家

我們想玩的是有角色、地方與人際依賴的復古 RPG。
採集或製作應幫助一次具體冒險；賣出物品應因另一位玩家需要它。
第一個問題：簡單畫面下，兩種職業能否讓玩家願意協商、交換，再出門一次？

目標玩家是願意參與 30 分鐘小型合作試玩的 2–4 位真人。
長期希望保留角色、職業、背包與交易歷史，逐步形成持久多人世界。
目前沒有 MMO 效能、同時在線人數或營運承諾。

## 2. 一場可觀察的故事

霧岸鎮外有礫坡與潮林，玩家接到修復觀測塔並取回路標的冒險。
礫坡產礦石，潮林產藥草；來回時間使採哪一條路有機會成本。
鐵匠製作修補組，藥師製作行路藥；兩者在塔路的不同危險中有用。
玩家可以先採自己的材料，也可以用委託換取缺少的物品。

出發者在鎮上開出固定報酬的製作單，另一名玩家完成並取得報酬。
兩人準備補給後走塔路，處理一場簡單戰鬥或路障，消耗藥劑與耐久。
回鎮後可修補裝備、交換剩料，選擇下一次要走的路。
主線獎勵是一次性來源；重複路線不無限鑄幣。

畫面只需俯視格子地圖、角色、資源點、背包、委託板與清楚的動作結果。
初期美術使用自有簡單幾何圖形與文字，仍要能看出所在位置和同行角色。
不能只交出試算表或交易表單，就宣稱這段 RPG 已可玩。

## 3. 靈感與原創邊界

參考 Blizzard 的職業設計：專精讓工匠有所區別，委託連接供需，品質影響用途。
本作只借用這些一般設計思路；職業、配方、數值、地圖、名稱及素材自行設計。
不複製 WoW 的角色、美術、任務、資料表或完整系統。

[OpenMMO Lab](../../openmmo-lab/docs/SDD.md) 保持固定上游的試跑範圍。
[Zircon-Godot](../../zircon-godot/README.md) 保持上游研究範圍。
本 lab 不依賴它們的 runtime，也不把研究成果標成已驗證遊戲。

## 4. 第一片範圍

| 面向 | 第一片 |
| --- | --- |
| 世界 | 一座鎮、兩個採集區、一條短冒險路線 |
| 角色 | 移動、少量生命值、背包、單一製作專精 |
| 職業 | 鐵匠、藥師；基本採集人人可做 |
| 製作 | 每職業兩個原創配方；普通／精製兩級 |
| 互動 | 固定價格製作委託、固定價格物品掛單、簡短訊息 |
| 冒險 | 一個可重現遭遇與一個需要補給的路障 |
| 持久化 | 角色、物品、貨幣、訂單、完成紀錄 |

不做拍賣撮合、浮動匯率、信用借貸、現金交易或代幣資產。
不做公會戰、龐大技能樹、開放世界生成或跨服交易。
不先做 NPC 商業代理、LLM NPC、多人副本或公網營運。

## 5. 經濟假設

### 5.1 專精與機會成本

每位角色首輪只選一個製作專精，試玩中不即時切換。
兩個資源區的產出不同；行走及背包容量形成取捨。
不以長時間等待來假裝深度，也不設必須付費跳過的阻力。
精製品先由明確配方及專精門檻決定，不使用隨機品質。
普通品仍能完成基礎冒險，精製品提供較長使用次數而非必需門票。

### 5.2 來源與消耗

| 資源 | 來源 | 消耗／去向 |
| --- | --- | --- |
| 原料 | 有界資源點再生、明確遭遇掉落 | 配方轉換、修補 |
| 消耗品 | 配方製作 | 使用後減量並記錄效果 |
| 裝備耐久 | 新裝備、修補 | 成功結算的冒險動作 |
| 貨幣 | 有限新角色補助、一次性任務 | 公開的掛單費、修理服務費 |
| 交易金額 | 玩家間轉移 | 除費用外不創造或銷毀貨幣 |

消耗應服務探索與選擇；不能只為維持價格而迫使玩家反覆做無趣工作。
NPC 不無限收購產物，也不以無限補助掩蓋缺少真人需求。
首次補助的發放以角色初始化紀錄去重；測試帳號不可冒充真人需求。

## 6. 提議架構

瀏覽器原生 HTML/CSS/JavaScript 呈現地圖與操作。
Python 3.11 標準庫 HTTP server 與 SQLite 是候選本機基線。
本次不加入依賴、不建立套件管理或服務。

伺服器擁有移動合法性、採集、戰鬥、製作、交易與消耗結果。
瀏覽器送動作意圖，不送可信的金額、掉落或任務完成狀態。
遊戲規則保留純函式；HTTP、時間與 SQLite 放在邊界。
第一片可用有界輪詢同步事件；是否需要 WebSocket 留待實測。

本機測試身份由伺服器建立並綁定角色，不宣稱 production authentication。
任何允許第二台機器連入的設定，須另有範圍與存取設計。

## 7. 資料與狀態

| 紀錄 | 必要欄位 |
| --- | --- |
| World | world_id、ruleset_version、schema_version、事件序號 |
| Character | character_id、位置、生命、專精、revision |
| Stack | owner_id、item_id、quality、quantity、revision |
| Wallet | owner_id、整數最小貨幣單位、revision |
| Order | order_id、種類、需求、品質下限、價格、escrow、狀態 |
| Action | actor、action_id、payload_digest、結果、事件序號 |
| Ledger | 動作、物品／金額變化、原因、來源／消耗類型 |

數量與貨幣只用有界整數；拒絕負值、溢位、未知物品和非有限數值。
配方定義確切投入與產出；原料轉換不是按物品件數簡單守恆。
每次製作必須符合固定配方的轉換向量。
貨幣守恆式是期末總額＝期初＋合法來源－合法消耗，包含 escrow。

訂單狀態為 open → filled，或 open → cancelled／expired。
開單時將報酬轉入 escrow；物品掛單則鎖定實物。
第一片不實作接單後長期占位；履約當下原子檢查並完成。
製作委託由工匠提供原料；介面顯示淨報酬和材料需求。
到期時間由伺服器判定；取消／到期只退還尚未履約的 escrow。

## 8. 原子性與失敗

SQLite 交易內完成資格檢查、revision 比對、扣料、交貨、付款及紀錄。
先持久化成功結果才回應；斷線不撤回已完成交易。
相同 actor/action_id 與相同 payload 重送，回傳原結果。
相同 ID 換 payload 必須拒絕，不能當成新動作。
兩人同時填同單只能一人成功；取消和履約也只能一方勝出。
失敗方不扣料、不收錢、不增加經驗或產物。

重連從已確認事件序號恢復，必要時取得完整角色快照。
普通重啟後讀取持久狀態；未提交交易全部回滾。
客戶端顯示待確認／已完成／拒絕，不以動畫結束當作持久化成功。
版本不符的命令拒絕並要求更新畫面。
既有世界的規則升級須有 migration 與回復計劃，不能靜默重算舊訂單。

## 9. 可觀察里程碑

| 階段 | 交付 | 通過證據 |
| --- | --- | --- |
| RE-0 | 固定配方、經濟事件與第一場劇本 | 規則表完整；來源／消耗可逐項核對 |
| RE-1 | 單人走路、採集、製作、遭遇、保存 | 瀏覽器完成一次路線，重啟狀態一致 |
| RE-2 | 兩角色訂單／交易與重連 | 同單競爭、回應遺失重送、取消競爭通過 |
| RE-3 | 2–4 真人短場試玩 | 保留結果與訪談；形成繼續／修改／停止決定 |
| RE-4 | 經濟壓力實驗 | 固定 seed 場景與失敗報告；不宣稱真人市場成立 |

每階段仍未啟動。沒有產品程式前不提供虛構的執行命令。

## 10. 驗收案例

- RE-A01：新玩家可在五分鐘內辨認目標、角色位置及下一步；記錄卡住原因。
- RE-A02：兩名真人完成一次採集→製作→委託→冒險消耗，能指出對方提供的價值。
- RE-A03：回應遺失後重送十次，產物、金額、經驗只變一次。
- RE-A04：兩個履約請求並行，只有一筆完成；失敗者庫存完整。
- RE-A05：履約／取消競爭後 escrow 歸屬唯一，總貨幣式成立。
- RE-A06：偽造角色、遠距採集、負數、超大數或錯誤品質需求均不改世界。
- RE-A07：在提交前後中止程序，重啟可分辨未完成和已完成，不複製物品。
- RE-A08：伺服器規則版本更新時，舊客戶端不按舊配方取得新產物。
- RE-A09：一次真正使用消耗品減少存量且產生對應冒險效果；無效使用不扣除。

## 11. 玩法與壓力證據分開

真人場記錄完成時間、非提示交易數、求助次數、空等時間與中途離開原因。
結束問每人：哪次決定有取捨？為何找另一人？願不願再玩一輪及原因？
首輪探索門檻：至少兩人走完整循環、發生一次非主持人代辦交易、無阻斷缺陷。
願意再玩和覺得有趣保留逐人原話；小樣本不估算留存率。
失敗照樣交付，不能刪掉不喜歡玩法的受試者。

模擬另外測三種情境：一區供給減半、單一角色囤積原料、重複獎勵導致通膨。
固定 seed、行動策略、回合數及初始資產，輸出缺貨時長、成交量、財富集中與貨幣總量。
機器人策略只驗規則與極端風險，不證明真人會交易或遊戲有趣。
供給衝擊不得靠未記錄的補貨修正；測試應暴露無法完成循環的情形。
