## Summary

Implemented manual archive retention with immutable issued plans and receipts, a database maintenance UUID, one-hour expiry, strict bounded approval validation, and atomic receipt/audit/tombstone writes. Preview records plan metadata without changing archive payloads. Apply revalidates the exact ordered candidates, verifies each actual payload's size and SHA-256 within a bounded read, and refuses the entire batch if any candidate changed or is unsafe. Completed-plan replay requires the same issued plan, valid lifetime/database identity, matching receipt and matching permanent tombstones.

Eligibility preserves interrupted/active runs, unfinished jobs, unknown/pending/mismatched ownership and unreleased reservations, and every export reference in every state. The normal fake provider's canonical `pending:<same run UUID>` handle qualifies only with matching fake backend/node/run/generation and confirmed stopped/released state; real provider pending handles remain protected. Migration advisory ownership, GC serialization and table locks include every eligibility table, including adapter history. A database insertion guard prevents an export approval from referencing bytes removed while that approval was waiting.

Archive metadata now includes nullable `pruned_at`; tombstone downloads return `410 artifact_expired`. Immutable identity metadata and all other run/job/binding/reservation/history records remain intact. Existing persistence refuses resurrection. ## Risks and Follow-ups

GC is manual, minimum 30 days, maximum 100 archives per approved plan. It takes bounded database locks and may return a sanitized database-unavailable error under contention; it does not retry or partially prune. It releases only archive payload bytes; retained run results/diffs and other history remain. PostgreSQL storage reuse does not promise immediate file shrink. Issued plan metadata and receipts remain permanent; broader history retention is separate work.

The worker used only synthetic databases and no live GitHub, real user records, runtime recovery, paid provider, credentials, deployment, commit or push. Full native/UI/browser/CI checks and independent delivery acceptance belong to the orchestrator.
