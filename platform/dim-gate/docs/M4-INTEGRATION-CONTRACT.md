## Shared data and API

`src/domain/schemas.ts` is the shared wire/domain source. Snapshot adds `entities.incidents`, `entities.integrations` and `observations.{buckets,traces,logs,recoveries}`. Bucket is a one-minute `[from,to)` window, with app/environment IDs, optional releaseId, rate req/s, errorRate fraction 0..1, p95Latency ms, source=demo. Unknown samples are null; absent samples give empty points. Trace has spans, optional CI and release references; logs are bounded safe messages with trace/release/CI links. Incident has ruleKey, episode, append-only evidence, assignee, relatedReleaseId and recoverySamples. Integrations have poolIds and a synthetic endpointLabel; never credentials or external requests.

The existing M4 read/command paths in SDD 06 become implemented. From < to, max24h, step60s; scope before filtering/counts, strict queries and stable pagination. Admin may read metrics/incident metadata, but cannot read raw trace/log or trace/log evidence IDs without an applicable RD/Ops grant. Unknown/scope-out detail is404. Lists, search, dashboard, guide, notifications and audit must also filter current project/stage scope. CI references are filtered by canReadCi; references cannot grant access.

Add `GET /notifications` returning scoped recent domain-event notifications `{items: Notification[]}` (maximum20, no hidden count). Each item has id/title/entityType/entityId/route/occurredAt, with a currently accessible detail link. Dashboard adds activeIncidentCount and pendingItems. Guide adds applicationId/environmentId (nullable) and steps with id/title/description/persona/completed/route; completion is a domain selector, never a UI checkbox. Steps must follow one coherent visible request/environment/release/incident chain, not mix unrelated applications. No unauthorized IDs or completion inference in Guide.

Client methods: getMetrics(window), listTraces(window+list filters), getTrace(id), listLogs(window+filters), listIncidents(filters), getIncident(id), acknowledgeIncident(id,expectedVersion,reason?), investigateIncident(id,expectedVersion,reason), listIntegrations(), testIntegration(id,expectedVersion), getNotifications(). `api.setScenario` accepts post-release-latency/recovery-samples with environmentId only. Query keys retain existing identity and revision invalidation. All clock controls retain shared pending ownership through response and refresh.

## State and deterministic time

One environment+ruleKey incident; p95>500ms OR errorRate>0.05 for3 consecutive minute buckets creates it. Rule key is `red-degradation`, evidence identifies each breached metric/threshold and sample window. Repeated abnormal evidence updates the existing active incident; after resolution new sustained abnormal samples reopen the same ID with episode+1. Null, missing or nonconsecutive observations cannot manufacture a recovery or threshold streak. Ops acknowledge/investigate requires current project/stage grants, expectedVersion and appropriate state; investigate/takeover requires reason. RD/Admin have no implicit incident write authority. Replay rechecks authorization before returning the original successful receipt.

Post-release-latency requires the currently active successful release and an idle ready environment. The explicit scenario injects three consecutive one-minute synthetic buckets (900ms/0.08/80req/s), traces and correlated logs. It advances180 demo ticks through the same central scheduler, assigning each sample its actual synthetic window; other in-flight work is advanced atomically too. Scenario receipt/audit describes only the authorized target. This is labeled simulated observation time, not three minutes of real measurements. Repeating it extends evidence without creating duplicate incidents.

Successful healthy rollback schedules three future one-minute recovery buckets (120ms/0.002/80req/s), one per60 demo ticks, after its health gate. The first two leave the incident active; the third consecutive healthy bucket resolves it. Failed rollback creates no recovery. Recovery for an obsolete release must stop if active release changes or a new abnormal scenario occurs. Historical abnormal buckets/evidence are retained. Explicit recovery-samples is a demo fallback for active incidents; it likewise goes through the observation engine with three minute buckets, not a direct resolved write. All scheduler/state/audit/idempotency/persistence changes commit together; storage failure leaves the entire prior snapshot intact. Recovery tasks are validated on reload, and reset clears them.
