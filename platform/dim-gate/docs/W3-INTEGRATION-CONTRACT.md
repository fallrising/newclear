## Canonical revision records

Revisions are new rows with distinct IDs; monotonic revision is per definition family or environment. `previousRevisionId`/`restoredFromId` point to immutable earlier content. Draft editing increments optimistic version; submitted/approved/executed content never changes. ### PipelineDefinition

Minimum source fields: applicationId, familyId, name, revision, requesterId, reason, state, spec, optional frozen specSnapshot, validationResult, decisions, correlationId and previousRevisionId. One active row per family; several named families may belong to one application. First creation allocates the family; revision copies retain it. Spec includes registered repositoryRef, safe refPattern (`main` or `release/*`), recipeRef (`demo-web-v1`), artifactRepositoryRef, targetEnvironmentIds and approvalPolicyRef (`independent-ops-prod-v1`). No repository URL or script input. All targets belong to that application and org; affected targets include the previous family revision's targets so removing a prod target cannot bypass prod governance.

States: draft→validated; if any affected target is prod, submit→pending_approval→approved/rejected. A different scoped Ops actor approves with reason. Explicit requester activation from validated nonprod or approved prod makes this row active and supersedes the previous active row atomically. Cancel applies before activation. Revisions retain a base-active guard; concurrent stale activation is409. Definition activation is metadata, not a deployment, and does not acquire a release execution lock.

New definition-run command requires an active definition, current RD scope, a ready selected target, environmentVersion, an allowed source ref and bounded sourceRevision. It invokes the existing five-stage pipeline and original prod Release approval/health semantics. Run saves definitionId, definitionRevision, sourceRevision and an immutable execution-relevant definition snapshot (registered repository/ref/recipe/artifact/policy values and selected environment, not unrelated target IDs/counts). Existing `revision` equals sourceRevision. Artifact digest remains produced by the existing package stage, never invented at trigger. Full definition history is independently immutable and scoped. Changing/activating a definition does not change old runs. Retry preserves the original run snapshot while rechecking current actor/environment/lock. Legacy `/pipelines` remains the existing explicitly registered recipe path with no fabricated definition fields.

### ServiceConfig

Fields add applicationId, environmentId, revision, targetEnvironmentVersion, baseActiveRevisionId and optional latestExecutionId. Spec is a bounded array of typed entries: key, description, and a discriminated valueType/value (`string`, finite bounded `number`, `boolean`, or `secretRef`). Keys have a safe bounded identifier syntax and are unique at validation. Secret references are selected only from registered fictitious, app/scope-compatible refs; no decrypted or secret-value input. Empty/missing active configuration is explicit, not a fabricated revision.

States: draft→validated→pending_approval (prod)→approved→applying→active/failed; nonprod applies from validated after explicit confirmation. Decisions need another scoped Ops actor. Apply rechecks source version, current RD/requester scope, prod decision, current approver scope, environment version, base-active revision and shared execution lock. A removed approver grant makes the old approval stale and requires a new revision/decision. Failure retains the previous active config. Success alone supersedes the old active and changes the environment version, while preserving activeReleaseId.

Use deterministic validate/render/activate execution steps driven by the shared logical clock. A targeted configure failure is a real failed attempt, with no partial active update. Restore creates a NEW draft revision from a selected historical config (`restoredFromId`); validate/prod approval/apply still apply. Normal revise also creates a new draft. No in-place history overwrite or one-click fabricated restore. Detail exposes a typed active/proposed diff; the UI can compare authorized environments of the same application without leaking hidden names/counts or treating unavailable data as empty.

### TrafficPolicy

Fields add applicationId, environmentId, revision, targetEnvironmentVersion, base effective-traffic guard and latestExecutionId. Spec includes a registered service endpointRef, registered path/host matchRef, exactly two distinct targetReleaseIds, nonnegative integer weights summing100, healthWindowSeconds, timeoutSeconds and typed p95LatencyMs/errorRate thresholds. Targets must be succeeded/healthy releases in this same app/environment with existing artifacts. The W3 supported final goal is candidate100, with the fixed10→50→100 progression; unsupported weight plans are explicitly rejected, not silently coerced. The form and schema disclose this bound.

The endpoint/match allowlist contains only safe fictional labels and known path/host matches; no arbitrary URL or platform adapter-route mutation. Actual network links, when present, derive from authorized canonical workload Placement/Relation/CI references; absent physical mapping remains explicit unknown. No network/ACL/DNS/gateway control is implied.

States: draft→validated→pending_approval (prod)→approved→rolling_out→active/failed; explicit nonprod start from validated. Prod needs another scoped Ops actor. Start rechecks requester/approver scope, target artifacts/releases, source/env/base-traffic guards and shared lock. Read distinguishes desired final weights, current step, last verified weights and actual data time. Traffic never rewrites activeReleaseId, Release state or artifact history.

Before any traffic policy exists, the Demo endpoint's fallback is explicitly the current verified activeReleaseId, if one exists; it is not measured traffic. Thereafter the effective distribution comes from the latest executed policy's last verified checkpoint, including a failed policy that previously verified10 before failing50. First-step failure retains its captured prior distribution. A new target pair cannot discard a still-weighted target; an incompatible residual distribution is409. Restarting after failure uses a new revision and independent prod decision, preserving old evidence.

Health uses deterministic, persisted, source-time-ordered Demo probe samples tied to policy/execution/step/candidate Release. They are not unrelated pre-start RED buckets. Window choices60/120/180seconds, cadence30seconds, at least window/30 consecutive known samples spanning the whole window; timeout is twice the selected window.
