## Fixed model and behavior

Snapshot v4/`dim-gate-w4-v1` adds `monitorPolicies`, `alertRules`, `sloPolicies`, `silences`, `alertEvaluations`, `notificationDeliveries` and bounded infrastructure metric samples. Retain strict frozen v3/v2/v1 readers and original bytes until an atomically validated upgrade succeeds. Add only empty collections in migrations; do not synthesize old alerts, approvals, incidents or grants. Existing entity IDs remain unchanged. All new entities carry canonical org, app/env or CI/object references, revision/version, timestamps and actor/correlation where applicable. Revisions are immutable after submission; edit or restore makes a new revision. Current active revision is explicit. Incident/evidence lineage stores the triggering `ruleId` and `ruleRevision`; legacy incidents remain valid and unchanged.

MonitorPolicy defines target kind (`service` app/env or `infrastructure` CI), registered source (`demo-red`/`demo-ci`), metric allowlist, sampling interval, enabled state and freshness. AlertRule references a MonitorPolicy and fixes metric, aggregation, window, comparator, numeric threshold with unit, consecutive known samples, severity, safe notification channel reference, and enabled state. SLOPolicy references a service MonitorPolicy and fixes indicator, target fraction, window and unit. No query DSL, arbitrary endpoint or external delivery. Service rules require RD project/stage write; infrastructure rules require Ops pool write. Reads require the corresponding current scope. Production service activation requires an independent Ops project/stage approval, actor unequal requester; Ops may not directly edit its service threshold. Nonproduction service and infrastructure activation have explicit validation and audit. Admin-only has no business execution grant. Recheck current policy, base version and idempotency for every command. Read outside scope is 404, denied write 403, bad DTO 422 and stale version/state 409.

Evaluation consumes persisted samples in source-time order; unknown, stale, missing or nonconsecutive samples cannot count as healthy or breaching. Every rule revision starts a separate evaluation lineage. The first qualifying breach creates one incident episode with immutable rule revision/evidence; further samples for the same open episode extend evidence without duplicate incident. Existing M4 rules and Release→metric/trace/log→Incident→Ops triage→RD evidence continue to work. Resolution still requires the existing healthy-sample rule; Silence never changes health, incident state or evidence.

Silence targets one rule and exact service environment or infrastructure CI, with reason, actor, start and expiry. Only a currently scoped RD service-rule owner or Ops infrastructure-rule owner may create it; maximum 24 hours. Active Silence suppresses notification dispatch only. Expiry uses the demo clock and restores evaluation for subsequent notifications; historical suppressed entries stay suppressed. A persisted Mock delivery record is queryable by scoped recipient with `queued`, `suppressed`, `delivered` or `failed` status, incident/rule revision, channel reference, time and safe failure code. Fixed channel refs are seeded and cannot be user URLs. A deterministic Demo failure scenario may produce `failed`; no real network call or external message.

## API and routes

Strict typed list/detail/commands, OpenAPI and runtime manifest use `/monitor-policies`, `/alert-rules`, `/slo-policies`, `/silences`, `/alert-evaluations`, `/notification-deliveries` with scoped filters. Commands support create, revise, validate, submit, approve/reject and activate where applicable; each has expectedVersion, reason and idempotency key, with command receipt and same canonical event/audit. Source detail includes active/evaluation/delivery state and availableActions. Registered routes are `/rd/apps/:appId/monitoring`, `/rd/apps/:appId/alerts` (`environmentId` query) and `/ops/alerting`; app/env mismatch is 404. Preserve current route keys/deep links. New route keys are `rd.monitoring`, `rd.alerts`, `ops.alerting`. UI must show sample freshness, unknown, rule revision, pending decision, Silence remaining time, delivery statuses and links to the original incident evidence. Commands close only after readback; denial/failure and refresh retain draft and history.
