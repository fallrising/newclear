## One source of identity, authorization and history

Existing User, Team, RoleAssignment, NavigationItem, Catalog and `policyVersion` remain canonical. W5 adds `source: seed | demo` to persisted User/Team. The v5 seed retains all accepted IDs and marks existing rows `seed`; a newly created User/Team receives a stable generated ID and `demo`, with no role assignment or Demo persona registration. Users have displayName, teamIds, enabled and version; teams have an existing businessUnitId, name and version. Admin may create demo Users/Teams, edit their display names and membership, and enable/disable users. No deletion, invite, password, email address, access token, SSO/SCIM/PAM or arbitrary role type. The fixed Demo persona allowlist remains separate, so storing a User never creates a login or impersonation path.

Only a currently enabled Admin with an org grant can mutate identity, assignments or governance. Every mutation has reason, expectedVersion where applicable, one canonical event/audit/receipt and idempotency key. Team membership never grants an action; only current RoleAssignment and its scope do. Existing create/revoke assignment commands remain the source of grants. All self-assignment/revoke and self-disable safeguards continue; the last enabled Admin cannot be disabled or lose the final Admin grant through any new path. User/team/assignment changes that affect eligibility increment `policyVersion`; commands and read projections recheck the current actor, recipient and scope. A menu or cohort does not elevate a denied API action. Read outside scope is 404; a known actor denied a write is 403; malformed DTO 422; stale version or incompatible state 409. Same-key/canonical-body replay returns the original receipt after current authorization without new writes; changed body conflicts.

Typed Admin list/detail/create/update routes are `/admin/users`, `/admin/users/:id`, `/admin/teams`, `/admin/teams/:id`. Existing `/admin/access` and `/admin/assignments` shapes and behavior remain compatible; the existing user PATCH gains optional displayName/teamIds while retaining enabled. Admin UI shows effective actions and the fact that a new User has no login/grant. Team membership and grant differences are visually separate. A disabled or revoked actor cannot revive an in-flight old dialog, cached response or notification by retrying.

## Registered feature cohort

`PlatformFeaturePolicy` stores an allowlisted `featureKey`, target center, optional eligible projectIds/teamIds, integer rolloutPercent 0–100, saltVersion, reason, requester, immutable revisions, activeRevision, version and `draft → validated → active/disabled` state. The code-owned feature registry fixes each key's supported center, action and UI route. It includes bounded W5 entries and an opt-in W4 monitoring/alerting entry; `admin.access`, `admin.navigation`, `/guide`, reset/recovery and the API base cannot be disabled or shadowed. Unknown keys, target mismatch and unsupported scope are 422; incompatible dependencies are 409. Revision/activation/disable has visible diff, reason, optimistic version and audit; restore creates a new revision. A policy absent for an accepted existing feature leaves that feature's W4 behavior available.

Cohort membership is a deterministic bucket derived from stable userId, featureKey and saltVersion; refresh, theme or order changes do not move a user. Eligibility is **current underlying grant/action ∩ capability support ∩ active cohort**. Preview lists only Admin-visible Demo users and the safe reason for each result, never hidden cross-org users. When a policy gates a command, domain authorization and current cohort are checked on the command itself, not only on navigation. Disable prevents new feature commands; an already approved or running Request/Release/Change/Traffic execution retains its frozen decision and remains readable to its current authorized owner. Feature changes never delete data or turn an unauthorized user into an RD/Ops operator.

## Registered Mock adapter routes and diagnostics

`PlatformRoute` references a code-registered routeKey, capabilityId, existing integrationId and adapterRef. The registry maps only fixed Demo inventory, observation and notification adapters to capabilities and safe fallback behavior. Route keys are not arbitrary pathnames, and adapterRef, destination label and diagnostic inputs are never URL/code/script/credential fields. Each route has bounded timeoutMs, enabled state, immutable revisions, activeRevision, health summary, version, actor, reason and audit. Admin may draft, validate, activate/disable and test a route; tests are deterministic local Mock results with revision and a safe failure/fallback code. No network proxy, DNS change, gateway, plugin execution or external fetch occurs. Duplicate keys, unsupported capability/integration, invalid timeout, alias loop and recovery/API-base override fail before activation. The simplest allowed registry may prohibit aliases entirely. Disabled/failing routes keep recovery/navigation reachable and do not silently claim success. Registry diagnostics are read-only mappings of capability, route, action, schema and adapter Mock health; unsupported capabilities retain explicit “later” labels.

Typed Admin routes are `/admin/platform-features`, `/admin/platform-features/:id`, `/admin/platform-routes`, `/admin/platform-routes/:id`, `/admin/platform-routes/:id/test`, and `/admin/capability-registry`. List/detail and command responses state draft/active revision and safe diagnostic result. UI routes `/admin/features` and `/admin/routes` are registered with fixed required actions; Admin route changes cannot rewrite the SPA route registry.

The read-only capability registry response groups `features`, `routes` and `later`. Feature rows name their route, action and schema; route rows name the fixed adapter and its current local diagnostic; the later rows have no executable route or adapter. Admin displays these mappings alongside route controls.

## Scoped notification configuration and attempts

W4's `NotificationDelivery`, AlertEvaluation, Silence, Incident and evidence remain valid, queryable history. W5 adds Admin-governed `Channel`, `NotificationTemplate` revision and `NotificationPolicy`, RD service/environment `NotificationSubscription`, and recipient-specific `NotificationAttempt` linked to the canonical W4 delivery or a clearly marked synthetic test event. Channels are metadata only: `in_app | demo_email | demo_webhook`, safe destination label, allowedProjectIds, enabled and version. There is no real address, webhook URL/token or outbound call. Policy fixes allowed severity/channel routing, bounded retention/dedupe and maximum Silence duration no greater than the accepted 24-hour W4 ceiling. Templates have a small safe placeholder allowlist and immutable revisions; no arbitrary HTML/script or raw trace/log/diff substitution. Existing `demo-rd`/`demo-ops` W4 refs migrate to safe seeded channel metadata without changing old delivery IDs or outcomes.

A subscription belongs to one currently scoped service environment and selects an enabled channel allowed for that project. Creation/revision requires current RD project/stage write; Ops infrastructure alert recipients are derived from current pool grants. Admin may manage channel/template/policy metadata but gains no implicit right to read or retry a private service delivery. Each attempt fixes sourceEventId, recipientId, channelId, templateRevision, status (`queued | suppressed | delivered | failed`), attempt number, timestamp and safe failure code. Initial logical delivery deduplicates by `(eventId, recipientId, channelId, templateRevision)`; retry creates a new attempt while retaining failed history. On dispatch and retry, recompute current recipient scope and channel policy and generate a fresh minimal projection for that recipient. Do not persist or replay an old private payload after grant, subscription or channel-scope revocation. Unauthorized list/detail/retry reveals no name, total, trace/log or raw diff. Silence changes dispatch only, never Incident health/evidence; expiry does not bulk-send suppressed history. Notification attempts cannot recursively trigger the same notification.

The policy's `dedupeSeconds` also coalesces a second W4 delivery for the same incident, recipient, channel and template revision inside that window; the original tuple remains idempotent without a time limit. `retentionDays` limits attempt list/detail/retry and attempt-audit visibility against the Demo logical clock. The persisted reference and W4 delivery history remain intact for migration and integrity proof, but an expired attempt yields no recipient-facing projection.

Admin UI `/admin/notifications` manages safe channel/template/policy metadata and Mock test delivery; RD extends its existing alerts page with scoped subscription and delivery readback; Ops extends `/ops/alerting` with recipient-safe delivery diagnostics and retry when currently authorized. A fixed failure scenario demonstrates `failed → new attempt` without real external delivery. All UI reports Mock status and source-time freshness, preserves draft on failure, and reads back after commands. Typed API/OpenAPI/runtime manifest cover all routes; no dynamic generic JSON endpoint or arbitrary destination.

## Snapshot, compatibility and gates

The new persisted format is strict `schemaVersion: 5`, `seedVersion: dim-gate-w5-v1`. Before additive v4→v5 migration, parse and run full v4 integrity on the original snapshot. v1/v2/v3 first use their existing strict versioned upgrades and then the same v4→v5 step. Add source metadata, safe seeded governance defaults and empty W5 work arrays only after original proof; reject reserved-ID collisions and invalid cross-references. Keep eager startup validation and preserve all W4 IDs, active work, revisions, events, audit and delivery history. `policyVersion`, idempotency and cancellation/reload semantics remain source-of-truth based.
