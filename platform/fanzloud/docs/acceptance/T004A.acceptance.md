# Scope

CU-CLOUD-P0-01 only: one trusted provider-specific runner for fixed Codex Cloud version, submit,
status, and bounded list operations. T004A owns the validated credential scope, diagnostic-write
sentinel, bounded process supervision, durable E2 submit ledger, same-operation replay, and
conservative reconciliation. Provider lifecycle decisions, diff retrieval, generic
`AgentBackend`, HTTP, browser state, local checkout, and `cloud apply` remain outside this task.

# Public API and Compatibility Review

The exported runner, configuration, cancellation, operation/request, submission, reconciliation,
and typed error values match SPEC-T004A. Every public T004A method carries its CU marker. The strong
submit operation ID rejects nil deserialization. Debug and errors omit prompts, raw streams,
environment/branch values, task summaries, cursors, URLs, and configured paths.

T004A reuses T002A scope validation and the T002B launcher policy rather than exposing another
executable, environment, cwd, shell, argv extension, or repository boundary. The shared capture
code now always joins both drainers. Explicit `LOCK_UN` in both credential-lease `Drop`
implementations closes a fork/exec inheritance race without weakening nonblocking exclusive
acquisition.

# Security, Atomicity, and Recovery Review

The runner persists `Intent`, `Authorized`, `Started`, and `TaskRecorded` before their corresponding
effect or success boundaries. Bare intent becomes terminal pre-start failure; any ambiguity after
authorization becomes durable `OutcomeUnknown` or `RecoveryRequired` if storage itself is
unavailable. Same-ID replay is observation-only, and neither bounded reconciliation nor zero, one,
or multiple candidates authorizes another Cloud exec.

Every real child uses the accepted private cwd, cleared environment with only `CODEX_HOME`, null
stdin, non-TTY pipes, a new process group, parent-death binding, deadlines, group termination, and
direct-child reap. The mode-`0700` `error.log/` sentinel prevents the pinned upstream append, and
the mode-`0600` single-link submit ledger uses synced atomic replacement.

# Fresh Review Findings

The first implementation review returned `IMPLEMENTATION REJECTED`. It correctly found that
malformed post-spawn exec output returned `ProviderOutput` instead of `OutcomeUnknown`, and that
P15 covered only one reconciliation candidate without a post-reconciliation retry assertion. Both
were corrected.

A fresh re-review returned `IMPLEMENTATION ACCEPTED`. A later repeated-suite run exposed a genuine
fork-inherited `flock` release race. The primary agent fixed the root cause with explicit unlock on
lease drop, ran the package suite ten consecutive times, and requested another fresh review. The
final review returned `IMPLEMENTATION ACCEPTED` with no blocker and confirmed T002A/T002B
compatibility.

# Non-blocking Observations

- A deterministic fork/pre-exec lease-inheritance regression could make the explicit unlock proof
  more targeted; ten consecutive parallel package runs currently cover the observed failure.
- `release_lock` cannot report its rare `flock(LOCK_UN)` failure through `Drop`; future operational
  telemetry may record it without logging paths or credentials.
- Direct partitions for `may_have_started: true`, duplicate task IDs across pages, and cancellation
  after authorization would strengthen already fail-closed branches.
- Started-commit storage failure returns `RecoveryRequired` and is promoted from durable
  `Authorized` to unknown on recovery; this safe asymmetry from the task-record failure path could
  receive a dedicated injected-fault test.
- The response-loss replay test reconstructs the request on the same runner rather than restarting
  the runner; the durable ledger is nonetheless reloaded on every submit call.
