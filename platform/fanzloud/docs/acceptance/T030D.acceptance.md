# Recovery, Security and Limitations

Open/save are E1; A/B replay pins a read-only transaction before reading identity so additive
migration cannot produce mixed schema observations. Durable history stays authoritative.
Full CHECK-enabled integrity runs on open. Snapshot save additionally scans cache-key metadata
with a fixed EXISTS query before accessing cache rows, rejecting structural key damage without
copying keys or bodies. This scan has constant application allocation but may inspect all cache
keys: the 4096-event bound applies to event-prefix verification, not cache-key inventory.

The 4096-prefix save ceiling and full verification do not accelerate startup. Save can hold the
writer lock beyond another writer's five-second wait; busy timeout bounds waiting, not operation
execution. At most 256 bounded event envelopes per page and 4096 total events are decoded.
Cache rows contain no event payload/credential/path/provider text. Malformed cache values do not
repair themselves; same-head bytes are immutable and cleanup is a separate future operation.

Dropped futures do not cancel blocking workers. Unknown completion may expose old or complete
new state; there is no automatic retry. Explicit same-input reconciliation at the original head
can be idempotent, while an advanced head conflicts. Schema rollback/crash leaves v0/v1 or exact
v2 and a safe private file; failed new open never unlinks another opener's database.

Deployment must quiesce legacy processes before upgrading. Already admitted legacy A/B access
can finish against unchanged events; this is not a mixed-version rollout guarantee. Downgrade
requires an operator backup or an existing v1 database, with no automatic reset/table deletion.
Private same-UID path replacement and filesystem sync honesty remain inherited non-guarantees.
