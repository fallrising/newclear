# Outcome

Execute only the pinned Codex Cloud version, submit, status, and list commands inside the accepted
credential scope, with bounded process supervision and a durable E2 submission ledger.

# Inputs

- TD §§1.6–1.7, 2.2–2.3, 8.2–8.10, 11.1–11.3 P14–P15, 14, and 15.0
- ADR-0002 §§Credential boundary, First execution interface, and Initial repository boundary
- Accepted T002 and T003

# Deliverables

- Fixed Cloud process runner over the existing validated `CredentialScope`.
- Administrator-only typed runner configuration containing the accepted scope, environment, and
  branch with a redacted debug boundary.
- Caller-created strong submit operation/request values whose same-ID replay can only return the
  durable prior outcome.
- Durable versioned submit ledger with intent, authorization, started, recorded-task, terminal
  pre-start failure, and unknown-outcome states.
- Bounded dual-pipe draining, deadlines, process-group termination, parent-death binding, and direct
  child reap.
- A validated private `error.log/` directory sentinel that makes the pinned upstream diagnostic
  append a no-op before any Cloud command executes.
- Bounded list reconciliation that never authorizes an automatic retry.
- Fake-CLI crash/fault/security tests, full P14, and TD-exact P15 regression coverage.

# Non-scope

Provider task lifecycle policy after a task ID is recorded, provider-side cancellation, diff
retrieval, `AgentBackend`, HTTP, browser state, local checkout, `cloud apply`, and any general
process or argv extension surface.

# Invariants

- Only accepted T003 invocations execute, with `env_clear`, only `CODEX_HOME`, and the private T002A
  working directory.
- Exact accepted login status is checked under the same lease before Cloud submit authorization.
- Submit intent and authorization are durable before spawn; a task ID is durable before success is
  returned.
- Any post-spawn submit failure without a durable task ID is `OutcomeUnknown`.
- Unknown submissions block another submit and are never retried automatically.
- The runner never executes repository-controlled code; the pinned cwd-relative diagnostic write
  is prevented before spawn.

# Dependency Evidence

passed fresh Cursor Agent design review. T004A implementation and its final fork-safe lease
release passed fresh Cursor Agent acceptance review.

# Risks and Gaps

Bounded list reconciliation cannot infer a unique provider task from title or time. The
specification therefore returns candidates, retains `OutcomeUnknown`, and exposes no retry
authority. This conservative behavior needs no provider correlation assumption.

# Design Review

The first fresh Cursor Agent review returned `DESIGN REJECTED`. It found that the public runner
constructor omitted administrator environment/branch configuration and that the P0 graph still
required generic backend conformance while recommending its deferral. The revision added
`CloudRunnerConfig`, exact login preflight, source-traced diagnostic prevention, distinct
launcher/orchestrator P15 tests, and ADR-0003's provider-specific P0 and managed-state E0 decisions.

The second fresh, read-only Cursor Agent review returned `DESIGN ACCEPTED` and confirmed that T004A
can be the sole Ready production task with no blocker before test-skeleton generation.

A final focused fresh review accepted the caller-created operation ID correction, required bare
pre-authorization `Intent` recovery to become `FailedBeforeSpawn`, and confirmed that the completed
19-test skeleton set permits production implementation.

The first implementation review rejected the post-spawn output error category and incomplete P15
partitions. Both were corrected. A fresh re-review accepted the implementation. After repeated
parallel testing found and fixed a fork-inherited lease-release race, a final fresh review again
returned `IMPLEMENTATION ACCEPTED` with no blocker. Evidence is recorded in
[`ACCEPT-T004A`](../acceptance/T004A.acceptance.md).
