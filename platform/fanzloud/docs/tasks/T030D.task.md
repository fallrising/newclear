# Outcome

Persist a versioned, discardable session snapshot cache after its missing concurrency and failure
semantics are resolved normatively.

# Inputs

TD §4.6 `save_snapshot(snapshot, expected_seq)` and accepted T030A.

# Deliverables

A future complete specification, snapshot value/codec, atomic save, conflict/crash/restart tests,
traceability, and acceptance.

# Non-scope

Durable event replacement, history deletion, reducer bypass, or treating snapshots as truth.

# Invariants

Durable events remain the source of truth and a failed snapshot operation cannot corrupt them.

# Dependency Evidence

T030A must be Accepted before implementation. This task is also blocked on the TD-GAP below.

# Decomposition

One snapshot-save state transition after its atomicity is decided.

# Machine Acceptance

To be fixed by the accepted specification after the TD-GAP is resolved.

# Required Documentation Updates

Resolve the gap through TD/ADR/specification review before marking Ready.

# Risks and Gaps

[TD-GAP: CU-EVT-04 / snapshot save concurrency and failure semantics]
Question: What does `expected_seq` compare, who wins concurrent saves, and what may a later load
observe after cancellation, timeout, or crash?
Known design: TD §4.6 says snapshots are caches, not sources of truth, but supplies no atomicity,
conflict payload, retry, monotonicity, or crash-visibility contract.
Candidate A: E1 compare the durable event-stream high-water to `expected_seq`, atomically replace
only with an equal/newer snapshot, and require re-read on conflict.
Candidate B: E1 compare only the prior snapshot sequence and allow snapshots behind current events.
Recommendation: Candidate A, because it prevents ahead-of-history caches and matches the append
conflict model, while still allowing event replay after the cached high-water.
Impact: Blocks T030D, T030C non-empty behavior, and T030 parent acceptance only.
