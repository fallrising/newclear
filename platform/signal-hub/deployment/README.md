# Optional expanded deployment preparation contract

Current personal use follows [SDD06](../docs/sdd/06-security-operations-acceptance.md), with one useful source and a non-root Docker or admitted OneFleet instance. This directory preserves worksheet v1 and the original expanded-operation preparation. It is optional for personal use, not native OneFleet configuration, a persistent Docker recipe or a deployment command. All worksheet gates default to pending; pending here does not block the reduced scope. See [design](../docs/m6-design.md), [acceptance and runbook](../docs/deployment-acceptance.md) and [runtime](../docs/runtime.md).

## Inspected lifecycle boundary

The existing OneFleet generic binary adapter launches `app`, sets `PORT` and uses the workload data directory as its working directory. Its remote systemd unit does not declare `User`, and the catalog CLI has no Signal Hub config/secret/mount/non-root flags. The raw hub binary needs explicit CLI paths. A wrapper alone does not repair host admission: the approved service UID, environment/path injection, mount permissions, isolation and tailnet ingress must be designed and reviewed before deployment. Do not issue a direct generic deploy as if these gates were met. For the OneFleet route, OneFleet stays lifecycle authority; privileged host work belongs to the host authority. The generic-adapter gap does not block a separately admitted personal Docker instance. `register` writes the catalog; `visibility=internal` is not a network ACL. No public ingress command belongs here.

## Frozen files and checker interface

- `intent.example.json`: our own versioned worksheet, with synthetic private-target placeholders, proposed launch inputs, fixed external-monitor budget and pending host/real M6 gates. This is not a native catalog/schema import.
- `config.example.json`: existing runtime config shape with synthetic source names and distinct runtime file references; no credential values.
- `launch.sh`: non-root launch template. Required explicit environment: `SIGNALHUB_SERVICE_UID`, `SIGNALHUB_BINARY`, `SIGNALHUB_CONFIG`, `SIGNALHUB_DB`, `SIGNALHUB_OWNER_TOKEN_REF`, `PORT`. Optional `SIGNALHUB_READONLY_TOKEN_REF`. It accepts no arguments, does not source config or eval text, requires normalized absolute readable inputs without symlink ancestors and an existing writable DB parent, validates UID/port, binds `127.0.0.1`, sets umask 077 and execs the binary. It never provisions/downloads anything, writes secrets, creates directories, starts a daemon or enables archive/backup automation. A prepared wrapper environment is an unresolved adapter/host approval gate.
- `python3 scripts/check_deployment.py [WORKSHEET]`: strict JSON and preparation structure checks; default file above. Prints preparation validity and pending gates. No network, writes, credential reads or deployment. A submitted passed gate must have complete evidence even without the option below.
- `python3 scripts/check_deployment.py --acceptance WORKSHEET`: requires `evidence_kind=real`, authorization references, all host gates and all four M6 evidence groups passed. Checks submitted timestamps/IDs/refs, seven elapsed days, all three sources, phone receipts, <=300-second hub outage notification and previous UTC-day restore. This is evidence-structure validation, never authentication or owner acceptance. Human review of original privately retained artifacts remains mandatory.
- `python3 scripts/test_check_deployment.py`: stdlib tests first cover premature acceptance, missing authorization/phone/outage, incorrect backup date and unsafe/root/missing launch inputs; a fake executable runs only in a self-owned synthetic directory. No accounts or services.

Worksheet v1 has exact top-level keys `version`, `evidence_kind`, `authorization_ref`, `target`, `launch`, `monitor`, `host_gates`, `m6`. `target` holds nonblank `node_ref`, `workload_ref`, `tailnet_acl_ref`, `archive_ref`, `backup_ref`, `rollback_ref`, hex `binary_sha256`/`config_sha256` and positive `schema_version`. `launch` holds `service_uid` (positive integer), absolute `binary`, `config`, `db`, `owner_token_ref` (`file:/absolute/path`), nullable `readonly_token_ref`, and `port` (1024..65535). `monitor` requires distinct host/process failure domain and notify path with fixed cadence 60s, deadline 10s, failures 2 and send budget 60s. `host_gates` is exactly `non_root`, `path_mounts`, `tailnet_ingress`, `independent_monitor`; each gate has `status=pending|passed`, nullable `evidence`. `m6` is exactly `seven_days`, `producer_silence`, `hub_outage`, `yesterday_restore`; each has `status=pending|passed`, nullable `evidence`. Pending evidence must be null. Passed evidence forms are documented in the acceptance runbook. Unknown fields, malformed dates and nonfinite JSON values fail closed. Synthetic packets cannot claim passed host or M6 gates.

## Required local verification

From component root: `python3 scripts/test_check_deployment.py`; `python3 scripts/check_deployment.py`; `sh -n deployment/launch.sh`; `git diff --check`; native `teamctl.py validate-report .team/reports/T-602.md`. Retain Red and Green logs under `.local/run/`; they are synthetic preparation evidence. The original expanded seven-day, phone, <=5-minute outage and previous-day restore criteria stay unverified; they are not the personal-use acceptance checklist.
