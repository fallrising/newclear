# M5 archive, consistent backup and isolated restore

This contract precedes implementation. Scope is AC-10–14 and preservation of M1–M4. No production operation, deployment, offsite service or runtime dependency is introduced. Archive and backup automation is opt-in through explicit directory flags; existing service invocations retain data until configured.

## Durable identities and projections

Migration 5 retains permanent event identities (`source`, `id`, original `seq`, canonical content hash, original received time/clock-skew and indexed event time) independently of hot payloads. Existing events seed this index. Normal ingest after purge still returns the original seq for an identical retry and records 409 for conflicting content. Never reuse a seq; subscription activation uses the durable high-water mark, including when hot storage is empty. Archive membership maps each part's ordered records to these identities. Metadata contains no tokens or notification credentials.

Import restores original identities/seq, sets hub metadata `restored: true` (outside the CloudEvent), and a restore retention deadline (default seven days, explicitly configurable on import). It never changes the original event content hash, producer freshness, subscription cursors or existing delivery bytes. Existing hot duplicates are left untouched; repeating import does not extend the deadline. `restored` is an optional boolean response field (absent/false for ordinary events), including detail and related events. New subscriptions and delivery projection scans exclude restored history. Rule evaluation preserves its existing hot-data semantics: restored rows participate in normal current-window evaluation and new-version automatic backfill; explicit backfill is needed to recompute older intervals outside that window. Existing pending/inflight/DLQ/succeeded messages, attempts, lease fences, replay ID and audit records survive purge and import unchanged. Delivery can continue from its materialized body even when the event detail is 404; importing restores that detail.

Purge must defer events still required by persisted immediate scan cursors or unmaterialized digest windows, including paused subscriptions which may resume. It also defers data needed by an active rule's pending backfill or catch-up/recomputation window. Conservative deferral is preferable to silently losing input. Retained rollups are not deleted. If recomputation would cross missing archived identities, reject the entire rule transaction with a sanitized instruction to import history first; never replace retained history with misleading zero counts. Importing the complete interval then permits backfill. Per-source retention uses the accepted persisted configuration, not an unaccepted file edit; unmatched/internal events default to 90 days. Overlapping matching source prefixes use the longest retention. Migrated source scopes defer purge until their first successful configuration reconciliation marks the persisted retention policy known; a legacy configuration hash alone cannot prove its accepted retention. Whole UTC days must be outside retention; never truncate extreme RFC3339 inputs, overflow day arithmetic, or form unsafe filenames. Archive filenames support UTC years 0001–9999; other accepted event times fail archival without deleting that data. Retention arithmetic is bounded to 3,660,000 days; larger configured policies fail safely instead of overflowing.

Event query cursors remain bounded and filter-bound. A deleted cursor position may return the existing invalid_query response; clients restart their query. Import is an explicit historical visibility change, so previously issued event cursors must not silently include newly restored rows: invalidate them using a persisted restore generation, or preserve equivalent snapshot semantics. No cursor resets subscription state.

## Archive transaction and recovery

`signalhub archive run --db DB --archive-dir DIR` processes eligible UTC days in seq order, bounded parts (at most 1,000 records and 16 MiB raw input per part, individual records at most 4 MiB). Raw CloudEvent objects are compacted into one JSON object per gzip line; original attributes and canonical content hashes remain identical. Files are `events/YYYY/MM/DD.part-N.jsonl.gz` relative to DIR. They contain no hub metadata. All parts are immutable: use exclusive publication, never overwrite existing paths, including orphan parts from interrupted runs. Reject symlink escapes and nonregular archive files.

Write and close gzip, fsync file and containing directories, reopen and validate gzip/strict event JSON, count, record identity/order and canonical hashes; compute SHA-256 of the complete compressed bytes. A successful database transaction records day/part/path/count/hash/first_seq/last_seq/created_at/verified_at plus exact membership, then deletes only the matching eligible seqs and sets purged_at. Assert deleted count equals manifest count. No range-based deletion of newly arrived events. Verification must use actual file bytes and trusted membership, not only two copies of computed metadata. No verified manifest or purge survives failure. Store transactions serialize concurrent archive/import and retain the original hot rows on write/read/validation/commit failure.

An interrupted pre-commit operation may leave an immutable orphan file. A retry uses a new part and does not trust or delete the orphan. A post-commit retry sees no eligible hot rows from the old part. Late events create another part of the same day. Restore expiry may likewise create a new part. `archive verify --day YYYY-MM-DD` verifies all recorded parts for the day against SQLite manifest/membership. Failures produce a bounded, sanitized `signalhub.archive.failed` event when the DB remains writable; successful nonempty runs produce `signalhub.archive.succeeded` in the same purge transaction; notice insertion failure rolls back the purge. No recursive archive failure retry.

`signalhub archive import --db DB --archive-dir DIR --day YYYY-MM-DD --reason TEXT [--retention-days 7]` requires a nonblank reason and imports only manifest-listed, fully verified parts into the associated database or its consistent restored copy. It is not a foreign/untrusted-file ingest API. Verify every part before transactional insertion; any mismatch/conflict rolls back the whole day. Audit `archive.import` with actor owner, day, reason, timestamp even for a successful zero-change repeat. File I/O resources/line sizes are bounded; no arbitrary SQL or archive path input.

## Backup and isolated restore

`signalhub backup --db DB --output NEW.sqlite` uses SQLite VACUUM INTO (or online backup), never copies a live WAL database file. Validate integrity, fsync and SHA-256 the completed snapshot, then exclusively publish it and a JSON checksum manifest; neither existing backups nor the source database may be overwritten. The snapshot includes identities, archive manifests/membership, rollups, all delivery/cursor/audit state and SQLite sequence high-water marks. Config and credential files are external and are not copied. An incomplete pair is unusable and fails verification; retain/report failure without touching existing files. Caller-provided existing DB paths must exist; maintenance typos must not silently create an empty DB.

`signalhub restore --backup SNAPSHOT --db NEW.sqlite --reason TEXT` verifies the manifest/hash and SQLite integrity, copies into a new destination using exclusive publication, then records `backup.restore` audit in the isolated copy. It never replaces an existing file or starts network activity. Original backup remains unchanged. The operator supplies separate synthetic credentials/config and an isolated archive directory copy to start a drill. Leases and at-least-once delivery semantics are preserved; no reset of attempts/cursors/DLQ. Restore into production remains an explicitly authorized operational action outside this milestone.

Server optional `-archive-dir DIR` / `-backup-dir DIR` run maintenance at startup and every 24h with cancellation and sanitized failures. Distinct output names are never overwritten. Failure of one operation must not prevent the other. No external scheduling/deployment or host change. Defaults do not enable deletion or backup without explicit directories. CLI maintenance holds local filesystem authority only, no HTTP mutation endpoint.

## Frozen worker interfaces

Store (T-501): `Archive(ctx, ArchiveOptions) (ArchiveResult,error)`, options `{Directory string; Now time.Time; DefaultRetentionDays int}`; result `{Parts []ArchiveManifest; Events int64}`. Manifest JSON fields day, part, path, event_count, sha256, first_seq, last_seq, created_at, verified_at, purged_at. `VerifyArchives(ctx, directory, day string) ([]ArchiveManifest,error)`. `ImportArchives(ctx, directory, day, reason string, now time.Time, retentionDays int) (ImportResult,error)`; result `{Imported int64; Duplicates int64}`. All require validated nonzero time, explicit archive directory; default retention zero resolves to90. T-501 owns store migration/identity/policy/query/subscription changes. T-502 owns only backup*.go in store plus CLI/runtime wiring and tests. Root owns contracts, docs and CI; T-503 owns real HTTP/browser verification and restored UI.
