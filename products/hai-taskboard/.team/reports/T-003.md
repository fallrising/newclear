## Summary

Recommended P0-A architecture: **Board-first project workspace with a selected WorkItem detail panel/page**. The Board remains the projection of the WorkItem phase and conditions; selecting a card opens its detail without turning logs, chat, or agent self-reported progress into the primary screen. At 320px, selection navigates to the same full detail page rather than preserving an unusable split view.

Two focused P0 architectures were compared:

| Candidate | Shape | Result |
| --- | --- | --- |
| A — Board-first workspace | Project switcher and Board are primary; selected card opens WorkItem detail; Attention and Impact are explicit secondary routes. | **Recommend.** Keeps operational state and WIP visible while retaining one place for all evidence and guards. |
| B — Attention/detail-first workspace | Attention inbox is the landing surface; selected WorkItem detail is central; Board is a secondary route. | Do not use for P0-A. It is useful during incident-heavy operation, but hides flow and invites event/notification-driven agent theater. |

P0 has four surfaces only: Project/Board, WorkItem detail, Attention inbox, and Impact preview. Run inspector, audit timeline, review, and evidence are tabs/sections of WorkItem detail, not separate navigation destinations. The recommended Board is a practical overview rather than a portfolio dashboard or chat-first screen.

### Board and WorkItem contract

- Board lanes represent the readable WorkItem phase: Draft, Ready, Developing, Review, QA, and Done. Blocked is a condition projection: a card with active blockers is placed in the Blocked lane/view by a documented priority rule and appears only once. It must not overwrite the WorkItem phase.
- Every card shows title, human owner, phase text/icon, effective validity, required AC coverage such as `2/3`, active-blocker count, last observed heartbeat, and the one pending action. Show no percentage unless its denominator and calculation are defined; never show agent self-reported progress as fact.
- Conditions are explicit, textual, and independently inspectable: stale has the accepted revision and cause path; disconnected has last synced cursor; an unknown execution outcome names the affected Run; cancellation says request pending rather than cancelled. Colour can reinforce these states but cannot be their only signal.
- WorkItem detail hierarchy is: (1) identity, goal, phase and active conditions; (2) next eligible action plus the exact guard/failure reason; (3) required AC coverage and current candidate/revision binding; (4) blockers/questions, owner, delegate and dependencies; (5) Runs, including input snapshot, heartbeat, cancellation/recovery and outcome; (6) Review/Evidence by AC; (7) immutable artifacts and audit timeline. This makes the completion gate inspectable before any completion control.
- Attention is deduplicated by its decision/question/blocker object, not by event. Each entry shows resolver, age, expiry, risk, cause, available action, snooze, and resolved history; snooze never resolves the blocker. Impact preview shows immutable old/new graph context, plan digest, affected items, cause path, and reusable/stale/unknown applicability. It must say `Unknown` where cost or reuse confidence is not known and must require a fresh preview after an `ImpactPlanStale` response.

### Shared transition interaction contract

Drag, keyboard, and single-click controls are three affordances for the same application command; none mutates the projection directly.

1. The user chooses a target phase by dragging, via keyboard move controls, or through a visible single-click “Move to…” menu plus previous/next buttons. The command carries the target phase, `expected_version`, and an idempotency key.
2. The client preserves the server-projected lane while the command is pending; it may show a labelled pending state but must not optimistically present a guarded transition as accepted.
3. On acceptance, the SSE/command result updates the canonical projection, announces success in an `aria-live` region, and moves focus to the updated card heading (or to the detail heading on narrow screens).
4. A rejected guard leaves the card in its authoritative lane. The focused control remains available and receives an inline, programmatically associated reason plus the permitted next action. For a Done rejection this names missing AC evidence, review, approval, stale input, or unresolved execution condition.
5. A `VersionConflict`/concurrent update is not silently retried: retain the user's target choice, show the current version and changed fields, offer refresh/review, and restore focus to the conflict message then the originating control. A command timeout/result-unknown shows “result pending verification” and provides re-query by the same command ID; it must not invite repeated submissions.

Keyboard movement is not the only drag alternative: all target moves are available as ordinary single-pointer clicks. Keyboard operation requires visible focus, semantic labels/instructions, `aria-live` success/failure feedback, and focus recovery. Narrow layout becomes list then detail; dark/light themes and zoom retain these controls and text labels.

### Required failure-state presentation

| State | Board/detail behaviour | Safe user action |
| --- | --- | --- |
| Disconnected SSE | Persistent `Disconnected` indicator and last synced cursor; cached content stays readable. | Reconnect/resync. Re-read current state before high-risk transitions. |
| Stale input/card | Name the accepted revision, changed dependency and cause path; evidence is visibly not currently applicable. | Inspect impact and refresh/rework; no publish or Done path from stale input. |
| Version conflict | Keep server state authoritative; show the competing update and field/version context. | Refresh/review, then submit a new explicit command. |
| OutcomeUnknown / needs reconcile | Run badge and Attention item identify uncertain side effect/observation; block automatic retry, publish, and Done. | Open Run recovery/reconciliation; do not infer that work did or did not run. |
| CancelRequested | Current phase remains visible with “cancellation requested; stop unconfirmed”; prohibit new dispatch. | Inspect/confirm stop or reconcile; do not label it Canceled early. |
| Done · Stale | Preserve completed history and CompletionRecord but mark it ineffective for the current baseline. | Inspect cause path; a human explicitly reopens only when appropriate. |

Monorepo UI conventions inform presentation, not product authority: Loom uses a compact flex-pane shell, compact bordered controls, monospace IDs, and explicit conflict banners. HAI should retain this dense, legible operational style while using semantic design tokens so its required light/dark themes, contrast, focus indicators, and non-colour state labels are met; Loom's current dark-only stylesheet is not itself a sufficient accessibility contract.
