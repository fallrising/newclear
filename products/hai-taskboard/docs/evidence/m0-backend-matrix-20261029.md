These proposals do not amend SDD or grant implementation acceptance.

1. **Preparation versus verdict.** `S/completion_description.go:61`: “DescribeCompletion is a snapshot for explicit operator intent, never a reservation or gate result.” It returns subject/rules/version/fence, verifies candidate bytes and repeats metadata reads; it never calls `EvaluateCompletion` and does not verify evidence reports or return per-AC reasons. `domain-and-gates.md` Evidence coverage requires “a stable coverage record for every required AC with the matching evidence IDs or a reason code.” Preserve the snapshot contract; M1a adds only authorized preparation transport. M2 must introduce a separate read-only authoritative coverage/predicate projection sharing completion inputs/material verification, and M3/M5 must not label preparation success as completion eligibility.
2. **Policy classification.** `docs/SDD.md:238` HAI-API-001 says “Validation, conflict, stale subject, policy rejection, unmet Done gate and storage corruption MUST have distinct stable error codes.” `S/completion_description.go:98-100` missing rule/zero environment returns `staleCurrentInput(nil)`; `S/current_input.go:50-52` first returns `lifecycle_rejected`, and `verifyCurrentRunInput:95-100` rewrites command errors to `stale_subject`; `S/service.go:609-612` has an alternative incomplete-policy `done_gate_unsatisfied` branch. Proposed M2 matrix: valid current binding with absent/unsupported policy rule→distinct policy rejection (exact wire spelling to be accepted); semantically changed captured/current input→`stale_subject`; malformed persisted canonical/normalized state→storage corruption; complete valid policy with insufficient evidence→Done-gate unsatisfied.
