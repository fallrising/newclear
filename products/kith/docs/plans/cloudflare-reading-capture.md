## 1. 要解決的問題

知識持續由 AI 整理，使用者需要一個在手機上願意每天打開的介面：讀整理後的文章、立即記下閃念、留下自己的修正，並知道內容在上次閱讀之後改了什麼。搜尋可以繼續交給既有 Agent；人的閱讀、批註與判斷需要留下可追溯的紀錄。

Kith 維持單 operator、邀請制的人機群聊用途。本計劃評估在同一專案重用適合的基礎能力，是否成為同一個應用程式或共用程式碼的分開部署，留待設計定案。

Ice Maker 繼續負責文件分析落地，Flowshot 繼續負責桌面閱讀器；本計劃不安排它們的功能、依賴或狀態變更。

## 2. 已確認的方向與待選的方案

### 使用者已確認的方向

1. 網站、閱讀、收件、批註與簡易頁面事件上報都以 **Cloudflare** 為安家位置。GitHub 仍保存內容與版本，自架 CI Runner 可負責匯出、建置與發布，不成為手機保存請求的同步前置。
2. 公開入口可直接閱覽，其餘私人資料入口需要驗證；公開範圍必須涵蓋正文、附件、索引及其他衍生產物。
3. 文章上方是 AI 整理區，下方是人類可追加、編輯的區域，中間有清楚分隔線。
4. 手機、Telegram、Slack 的原始輸入先持久化，第一次保存不經 AI。分類及 AI 整理可以在之後進行。
5. GitHub Actions 自動更新閱讀內容，日常使用不依靠手動 reload 按鈕；手機快記優先。
6. 使用簡單自寫 JavaScript 監聽頁面事件並上報 Worker 是可接受的方案，不要求完整 Umami 相容性。
7. 優先評估 Kith 的重用空間；沿用使用者現有訂閱 Agent 的工作方式，不新增付費 LLM API 呼叫或 provider 依賴。

### 本文提出、尚待定案的方案

- 用 D1 接住原始輸入、人類批註與閱讀狀態，再非同步匯出 Git。
- 同一份程式碼分別部署公開與私人閱讀介面，公開部署只取得公開產物。
- AI 正文與人類補充各自保存、各自版本化，畫面合成一篇文章。
- CI 固定來源 commit 建置可重現的閱讀版本；手機取得小目錄與版本資訊，正文按需載入。
- 簡易事件統計寫 D1，先做必要的彙總；分析失敗不影響保存或閱讀。

以上是設計候選。D1 與 Git 的權威邊界、認證方式、路由及資料表都要先定清楚，才轉成實作契約。

現有 Kith 的 D1 `messages` 是聊天室耐久 log，Room DO 管理順序、成員與廣播。快記保存不能僅以「丟一則聊天室 message」代替：那會帶入房間可見性、attention 喚醒及聊天生命週期。人類原文需要自己的保存與保留契約。

現行 [v2 00 §4](../v2/00-overview.md) 與 [BR-32／BR-37](../v2/01-domain.md) 仍把聊天訊息編輯、伺服器已讀回執、Telegram 橋等列為非目標。新模組的筆記編輯、文章閱讀版本與收件 adapter 必須明確定義範圍，不能默默改變聊天室語意。

Kith 現行 SDD 以 Workers Paid 為核心部署畫像。這次採 **free-tier-first 的新模組評估**，不宣稱整套既有 Kith 已可免費運行，也不自行把帳號升級。若某條重用路徑超出預算，先測量並提出簡化方式；必要時共用 UI 程式碼而分開部署輕量 Worker。

## 4. 候選的資料與操作流程

### 4.1 保存原文

手機快記或受驗證的通訊入口 → Worker → 耐久保存 → 回傳穩定 `capture_id` 與保存狀態 → 後續 Git 同步／AI 整理。

最低資料包含原文、輸入來源、原始時間與冪等鍵。來源訊息編輯保留為版本；重送依來源事件 ID 去重。AI 產物連回原始輸入，不覆蓋原文。介面區分「本機草稿」「已保存」「已同步 Git」「已整理」，避免把 CI 已排隊當成原文已保存。

初期建議 D1 保存收件資料及待同步紀錄。一個待同步項對應穩定檔名或紀錄 ID；Runner 重試前查驗既有結果，恢復時可掃描未完成項，不只依賴一次通知。

**待定：** Git 是否只收單向匯出，或允許直接修改後匯回。正文、原文、批註與閱讀狀態各自只能有明確的寫入權威；雙向同步若要做，先定版本衝突與刪除語意。

### 4.2 自動更新閱讀內容

來源 Git 版本 → CI 建置 → 驗證公開範圍與連結 → 發布閱讀產物。產物記錄來源 commit／建置版本。失敗時維持最後一次成功版本，新原文仍能在收件匣查看。

手機開啟或回到前景時自動檢查版本；文章按需載入。正在閱讀的正文與位置保持穩定，切頁或接受更新後再換版本。檔案改名時使用穩定文章 ID 保住批註與閱讀紀錄。

自架 Runner 的用途是 Git 同步與建置；Codex、shell、Git workspace 仍不在 Worker 中執行。新的發布工作流需在之後另行設計，現有 [Kith CI](../../../../.github/workflows/kith.yml) 是驗證用途，不在本次改成部署工作流。

### 4.3 公開與私人閱讀

優先評估兩個部署共用程式碼：公開部署只接收選出的公開稿，私人部署提供完整授權內容及寫入介面。若選同站分路徑，也必須在資料 API、靜態資產與衍生索引上一起驗證存取範圍。

Cloudflare Access 可作為候選入口驗證；它如何與 Kith session、member／operator 權限共存需要設計，不能把「通過 Access」直接等同「可讀每個私人來源」。Webhook 使用服務自己的驗證及允許的來源身份，不靠互動式登入頁收件。

公開稿及人類批註各自決定可見性。私人來源未經選取不進公開建置；搜尋索引、附件、RSS、sitemap、反向連結也遵循同一份公開範圍。

### 4.4 AI 正文與人類補充

畫面保持「AI 在上、人類在下」；資料層優先評估兩份內容依文章 ID 組合，並保留同一 Markdown 分區的簡化選項。單一檔案分隔線不是寫入權限控制，實作需能阻止 Agent 的一般整理路徑覆蓋人類原文。

批註記錄所針對的正文版本；修改批註保留歷史。重要異議在文章上方也有提示。AI 根據批註修正後，可以標示該批註針對舊版本，由人判斷是否已解決。

閱讀紀錄要能識別當時呈現的 AI 正文與人類補充版本。「開啟過」「明確標記讀過」「我有疑問」是不同事件；不把滾動或停留時間自動當成理解或認同。

### 4.5 自寫頁面事件統計

瀏覽器 JavaScript 監聽有限事件，例如開啟文章、達到選定閱讀位置、回訪；以小批次上報 Worker，寫入選定的 CF 儲存並產生簡單彙總，D1 是優先評估的選項。可使用 `sendBeacon` 或 `fetch`，但上報成功不是筆記或已讀狀態的保存保證。

分析事件只帶必要的文章 ID、事件類型、版本與時間資訊；不送正文、輸入內容、私人標題、完整 URL、query 或 referrer。公開與私人分析分開處理。限制單次大小、批次量、頻率、查詢與保留期，避免每次 scroll 都寫一筆資料。

明確已讀、批註與保存結果走具備身分驗證、冪等處理的應用 API。統計上報可停用、可遺漏，不能影響寫筆記。第一版不要求安裝完整 Umami、PostgreSQL 或 VPS 上的分析服務，也不需要 session replay。

## 7. 後續實作的驗證原則

沿用 [AGENTS](../../AGENTS.md) 與 [v2 E2E 規則](../v2/08-testing-e2e.md)：文件先行、失敗模式先行、以隔離環境和合成資料驗收。新的閱讀／收件功能至少覆蓋保存回應遺失後重送、D1／Git 結果未知、Runner 離線後恢復、兩端版本衝突、公私衍生產物、Agent 誤寫人類區、分析服務不可用及停用付費呼叫等情境。

實作時按當前切片跑對應 E2E，保留原有回歸；完整套件交由 PR／CI gate。不得把文件中的預期行為當成已完成測試。本次只新增設計文件，沒有更改程式、依賴、遷移、feature flags、部署或 Agent runtime。
